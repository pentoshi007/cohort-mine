## 1) Goal and Architecture

You are deploying a monorepo with three runtime services:

- `apps/web` -> Next.js frontend (port `3000`)
- `apps/backend` -> Express API (port `8080`)
- `apps/websocket` -> Bun WebSocket server (port `8081`)

All services share one package:

- `packages/db` -> Prisma schema + migrations + generated client export

High-level deployment flow:

1. Push code to `main`
2. GitHub Actions builds Docker images
3. Images are pushed to Docker Hub
4. VM pulls latest image
5. VM replaces old container with new one

## 4) Step 1 - Create Monorepo and Workspace Baseline

From scratch:

```bash
npm create turbo@latest
```

Choose:
- package manager: `bun`
- apps/packages workspace layout

Root `package.json` key points:

- `"workspaces": ["apps/*", "packages/*"]`
  - tells Bun/npm where workspace packages live
- `"build": "turbo run build"`
  - builds all packages/apps with dependency graph support
- `"dev": "turbo run dev"`
  - runs all dev scripts in parallel
- `"db:generate": "cd packages/db && npx prisma generate && cd ../.."`
  - generates Prisma client before runtime/build

Why this matters:
- in monorepos, shared package compile/generate steps must run before app runtime
- Turbo helps order task execution

## 5) Step 2 - Build the Shared DB Package with Prisma

Create DB package:

```bash
cd packages
mkdir db
cd db
bun init -y
bun add prisma @prisma/client
bunx prisma init
```

In `packages/db/prisma/schema.prisma`, configure:

- generator:
  - `provider = "prisma-client-js"` -> generates JS client
- datasource:
  - `provider = "postgresql"`
  - `url = env("DATABASE_URL")`
- models:
  - `User` and `Todo` with relation

In `packages/db/index.ts`:

```ts
import { PrismaClient } from "@prisma/client";
export const prismaClient = new PrismaClient();
```

In `packages/db/package.json`:

```json
"exports": {
  "./client": "./index.ts"
}
```

Why export map matters:
- consumers can import via `db/client`
- stable package API for workspace apps

## 6) Step 3 - Run PostgreSQL in Docker and Connect Prisma

Start PostgreSQL:

```bash
docker run -e POSTGRES_PASSWORD=mysecretpassword -d -p 5432:5432 postgres
```

What each part does:

- `-e POSTGRES_PASSWORD=...` -> sets DB superuser password
- `-d` -> detached mode
- `-p 5432:5432` -> map container port to local machine
- `postgres` -> image name

Set `.env`:

```env
DATABASE_URL="postgresql://postgres:mysecretpassword@localhost:5432/postgres"
```

Prisma reads this variable while migrating/generating and runtime DB queries.

## 7) Step 4 - Generate Migration and Prisma Client

From `packages/db`:

```bash
bunx prisma migrate dev --name init
bunx prisma generate
```

What is created:

- migration SQL at `packages/db/prisma/migrations/.../migration.sql`
- generated Prisma client in `node_modules/.prisma` + `@prisma/client`

In this project, migration SQL creates:
- `User` table
- `Todo` table
- foreign key `Todo.userId -> User.id`

Why `generate` is repeated in Dockerfiles:
- fresh build environment does not reuse local generated client
- CI image must generate its own Prisma artifacts

## 10) Step 7 - Deep Dive: Root DevOps Config Files

### `turbo.json`

Important sections:

- `"tasks.build.dependsOn": ["^build"]`
  - build dependent packages first
- `"tasks.build.inputs": ["$TURBO_DEFAULT$", ".env*"]`
  - env changes can invalidate cache
- `"tasks.build.outputs": [".next/**", "!.next/cache/**"]`
  - cache Next build output, skip cache folder
- `"tasks.dev.cache": false`
  - dev should not be cached
- `"tasks.dev.persistent": true`
  - long-running dev process

### `.dockerignore`

Current file contains:

```txt
node_modules
```

Meaning:
- Docker build context excludes host `node_modules`
- reduces context size and avoids copying incompatible binaries

Recommended to add:
- `.git`
- `.turbo`
- `dist`
- `.next`
- logs
- local env files if not needed at build

## 11) Step 8 - Deep Dive: Dockerfile.backend (Line by Line)

File: `docker/Dockerfile.backend`

```dockerfile
FROM oven/bun:1
WORKDIR /usr/src/app
COPY ./packages ./packages
COPY ./bun.lock ./bun.lock
COPY ./package.json ./package.json
COPY ./turbo.json ./turbo.json
COPY ./apps/backend ./apps/backend
RUN bun install
RUN bun run db:generate
EXPOSE 8080
CMD ["bun", "run", "start:backend"]
```

Explanation:

1. `FROM oven/bun:1`
   - base image with Bun runtime installed
   - pins major line `1`; for reproducibility prefer exact version tag

2. `WORKDIR /usr/src/app`
   - all next commands run from this folder

3. `COPY ./packages ./packages`
   - includes shared packages (`db`, configs, ui)
   - backend depends on `packages/db`

4. `COPY ./bun.lock ./bun.lock`
   - lock dependency versions in image builds

5. `COPY ./package.json ./package.json`
6. `COPY ./turbo.json ./turbo.json`
   - workspace metadata and task graph available in image

7. `COPY ./apps/backend ./apps/backend`
   - copy only backend app, not all apps

8. `RUN bun install`
   - installs all workspace dependencies needed by copied workspaces

9. `RUN bun run db:generate`
   - generates Prisma client before runtime
   - without this, app may crash on DB import

10. `EXPOSE 8080`
    - documents container port (does not publish by itself)

11. `CMD ["bun", "run", "start:backend"]`
    - container startup command

Build command:

```bash
docker build -f docker/Dockerfile.backend -t todo-backend:local .
```

Run command:

```bash
docker run --rm -p 8080:8080 --env-file .env todo-backend:local
```

## 12) Step 9 - Deep Dive: Dockerfile.frontend (Line by Line)

File: `docker/Dockerfile.frontend`

```dockerfile
FROM oven/bun:1
WORKDIR /usr/src/app
ARG DATABASE_URL
COPY ./packages ./packages
COPY ./bun.lock ./bun.lock
COPY ./package.json ./package.json
COPY ./turbo.json ./turbo.json
COPY ./apps/web ./apps/web
RUN bun install
RUN bun run db:generate
RUN DATABASE_URL=${DATABASE_URL} bun run build
EXPOSE 3000
CMD ["bun", "run", "start:web"]
```

Explanation:

1. `ARG DATABASE_URL`
   - build-time variable
   - only available during `docker build` steps
   - not automatically available at runtime

2. `COPY ...`
   - includes shared packages + web app

3. `RUN bun install`
   - install dependencies for build

4. `RUN bun run db:generate`
   - ensure Prisma client exists for Next server-side code

5. `RUN DATABASE_URL=${DATABASE_URL} bun run build`
   - inject DB URL into build environment for Next build stage
   - important if build-time data fetching uses DB

6. `EXPOSE 3000`
   - frontend listens on port 3000

7. `CMD ["bun", "run", "start:web"]`
   - starts production Next server

Build command:

```bash
docker build -f docker/Dockerfile.frontend --build-arg DATABASE_URL="$DATABASE_URL" -t todo-frontend:local .
```

Run command:

```bash
docker run --rm -p 3000:3000 --env-file .env todo-frontend:local
```

Important beginner concept:
- `ARG` is build-time
- `ENV` is runtime (unless overridden)

## 15) Step 12 - Deep Dive: `cd_backend.yml` (Line by Line)

File: `.github/workflows/cd_backend.yml`

```yaml
name: Deploy the backend
on:
  push:
    branches: [ main ]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout the code
        uses: actions/checkout@v2

      - name: Docker login
        uses: docker/login-action@v2
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v4
        with:
          context: .
          file: ./docker/Dockerfile.backend
          push: true
          tags: 100xdevs/todo-app-backend:${{ github.sha }}

      - name: Deploy to the VM
        run: |
          echo "${{ secrets.SSH_PRIVATE_KEY }}" &> ~/ssh_key
          chmod 700 /home/runner/ssh_key
          ssh -o StrictHostKeyChecking=no -i ~/ssh_key root@64.227.169.180 -t "docker stop user_backend && docker run --name user_backend -d -p 8080:8080 100xdevs/todo-app-backend:${{ github.sha }}"
```

Key-by-key explanation:

- `name`
  - workflow display name in Actions UI
- `on.push.branches: [main]`
  - triggers only on pushes to `main`
- `jobs.build`
  - one job called `build`
- `runs-on: ubuntu-latest`
  - GitHub-hosted Linux runner

Steps:

1. checkout
   - fetches repository contents to runner filesystem

2. docker login action
   - authenticates with Docker Hub
   - needed before `push: true`

3. build-push action
   - `context: .` -> entire repo as build context
   - `file: ...backend` -> backend Dockerfile path
   - `push: true` -> upload built image to registry
   - `tags: ...:${{ github.sha }}` -> immutable image per commit

4. VM deploy shell step
   - writes SSH private key from secret
   - changes permission for SSH key usage
   - SSHs into VM and executes Docker command

Risk in current command:
- `docker stop user_backend && docker run ...`
  - if container does not exist, stop fails and run never executes
- safer:
  - `docker stop user_backend || true`
  - `docker rm user_backend || true`
  - then `docker run ...`

1. Wrong Dockerfile path:

- image `todo-app-backend`
- port `8080`

For websocket it should use:
- container name like `user_ws`
- image `todo-app-websocket`
- port `8081:8081`

3. Same `docker stop && docker run` reliability issue as backend

## 19) Step 16 - VM Deployment Sequence

2. `cd_ws.yml` deploy command points to backend image/container/port

## 21) Step 18 - Recommended Production Hardening

1) Pin versions:
- `actions/checkout@v4`
- `docker/login-action@v3`
- `docker/build-push-action@v6`

2) Add health checks:
- container-level healthcheck in Dockerfile or runtime
- post-deploy check endpoint

3) Add rollback strategy:
- keep previous SHA
- on failure, redeploy previous image

4) Add `concurrency` in workflows:
- prevents overlapping deploys

5) Use least-privilege deploy user:
- avoid root SSH if possible

6) Separate build and deploy jobs:
- clearer pipeline, easier retries

7) Use immutable tags + optional floating tag:
- always push SHA tag
- optionally push `latest` only for one branch/environment

## 23) Troubleshooting Playbook

### Build fails with Prisma client errors

Cause:
- `prisma generate` not run inside image

Fix:
- keep `RUN bun run db:generate` in all Dockerfiles

### Frontend build fails with DB errors

Cause:
- missing `DATABASE_URL` build arg

Fix:
- pass `--build-arg DATABASE_URL=...`
- verify workflow has `build-args`

### SSH deploy fails

Cause:
- invalid key permissions, wrong host/user, blocked SSH

Fix:
- confirm `SSH_PRIVATE_KEY` secret
- ensure VM firewall allows SSH
- test manual ssh from local machine

### Container replacement fails

Cause:
- using `docker stop name && docker run ...` and old container absent

Fix:
- use `docker stop name || true`
- use `docker rm name || true`
- then run new container

### Wrong service deployed

Cause:
- image tag/container names copied from another workflow

Fix:
- keep unique image/container naming per service
