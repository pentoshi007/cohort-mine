## 1) Docker in one line

Docker is a way to run your app in a sealed box so it works the same on every machine.

Think:

- your laptop = city
- your app = shop
- Docker container = rented shop room with fixed setup

If another developer opens the same container, they get same setup.

---

## 2) Core words (very important)

### Image

An image is a template or blueprint.

- It is not "running".
- It is like a class in programming (definition only).

### Container

A container is a running instance of an image.

- It is live.
- It has process, memory, logs, and temporary writable space.

### Volume

A volume is persistent storage managed by Docker.

- Container can die.
- Volume can survive.

So DB data should go to volume, not only container writable layer.

### Network

A Docker network is a private communication lane between containers.

- Containers in same network can talk by service/container name.
- Example: app can connect to DB host `postgres`.

### Dockerfile

`Dockerfile` is instructions to build one image.

### docker-compose.yml

`docker-compose.yml` is instructions to run multiple services together.

## 3) Why developers use Docker

Without Docker:

- "Works on my machine" problem
- different Node/Bun versions
- different OS packages

With Docker:

- same runtime everywhere
- easier onboarding
- easier CI/CD automation

## 4) Docker layers (easy mental model)

When building image, each instruction creates a layer.

Example:

- `FROM ...` (base layer)
- `COPY package.json bun.lock ...`
- `RUN bun install ...`
- `COPY src ...`

If source code changes but dependency files do not change, Docker reuses cached dependency layers.

Result: much faster rebuild.

## 5) Read this project Dockerfile line by line

File: `27-week-27/27.1-docker-compose-example/DockerFile`

```dockerfile
FROM oven/bun:1-alpine

WORKDIR /app

COPY package.json bun.lock ./
RUN bun install --frozen-lockfile

COPY prisma ./prisma
COPY prisma.config.ts ./
COPY src ./src
COPY tsconfig.json ./
```

What each line means:

  - start from Bun base image.
  - `alpine` means small Linux image.

- `WORKDIR /app`
  - set working folder inside container.

- `COPY package.json bun.lock ./`
  - copy dependency definition files.

- `RUN bun install --frozen-lockfile`
  - install exact locked dependency versions.

- `COPY prisma ...`, `COPY src ...`, etc.
  - copy your app code and Prisma files.

- `RUN bunx prisma generate`
  - create Prisma client code inside image.

- `EXPOSE 3000`
  - says app uses port 3000 internally.

- `CMD ...`
  - when container starts:
    1) apply DB migrations (`migrate deploy`)
    2) start app (`bun src/index.ts`)

## 6) Read this project docker-compose.yml line by line

File: `27-week-27/27.1-docker-compose-example/docker-compose.yml`

```yaml
services:
  postgres:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: usersdb
    ports:
      - "5432:5432"
    volumes:
      - pg-users-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d usersdb"]
      interval: 5s
      timeout: 5s
      retries: 10
      start_period: 5s

  app:
    build:
      context: .
      dockerfile: DockerFile
    restart: unless-stopped
    depends_on:
      postgres:
        condition: service_healthy
    environment:
      DATABASE_URL: postgresql://postgres:postgres@postgres:5432/usersdb?schema=public
      PORT: 3000
    ports:
      - "3000:3000"

volumes:
  pg-users-data:
```

Simple meaning:

- `services` = containers to run.
- `postgres` service = database container.
- `app` service = your API container.
- `volumes` = persistent storage declarations.

Important parts:

- `ports: "5432:5432"` on postgres
  - left side = host port
  - right side = container port

- `pg-users-data:/var/lib/postgresql/data`
  - DB data stored in Docker volume `pg-users-data`.

- `depends_on ... service_healthy`
  - app waits until postgres healthcheck passes.

- `DATABASE_URL ... @postgres:5432`
  - app connects to DB using service name `postgres` (Docker DNS).

## 7) Network explained for beginners

### Why not `localhost` inside app container?

Inside container, `localhost` means the same container, not your laptop and not postgres container.

So app container should use:

- `postgres` (service name) in Compose setup.

### `host.docker.internal` meaning

When container needs to talk to something running on host machine, use `host.docker.internal` (Docker Desktop feature).

Use cases:

- app container + DB started separately on host mapped port

## 8) Volume explained for beginners

If you store DB only in container writable layer:

- delete container -> data gone

If you store DB in named volume:

- delete container -> data stays
- recreate container with same volume -> data returns

This is why databases should use volumes.

## 9) Commands: what each one does

### `docker build -f DockerFile -t user-project:test .`

- `docker build` = build image
- `-f DockerFile` = use this dockerfile name
- `-t user-project:test` = tag image with name:tag
- `.` = build context (current folder files available to COPY)

### `docker run -d --name pg-users ... postgres:16-alpine`

- `docker run` = create + start container
- `-d` = detached (background)
- `--name pg-users` = container name
- `-e KEY=VALUE` = environment variable
- `-p 5432:5432` = host:container port mapping
- `-v pg-users-data:/var/lib/postgresql/data` = named volume mount
- last token `postgres:16-alpine` = image to run

### `docker compose up --build -d`

- `docker compose up` = start services from compose file
- `--build` = rebuild images before starting
- `-d` = run in background

### `docker compose down`

- stop and remove containers and network created by compose
- volumes stay unless `-v` added

### `docker compose down -v`

- same as above + remove named volumes from compose
- DB data will be deleted

## 2) Docker Core Theory (What, Why, How)

### What problem Docker solves

Without Docker, apps may fail due to environment drift:

- different OS packages
- different runtime versions
- different local setup steps

Docker packages the app runtime and dependencies so the same setup can run on any machine with Docker.

### Key terms

- `Image`: Read-only packaged blueprint.
- `Container`: Running instance of an image.
- `Volume`: Persistent storage managed by Docker.
- `Network`: Virtual network for container-to-container communication.
- `Registry`: Image hosting system (Docker Hub, GHCR, ECR, etc.).

### Typical lifecycle

1. Build image (`docker build`)
2. Run container (`docker run`)
3. Inspect logs/state (`docker logs`, `docker ps`)
4. Stop/remove container (`docker stop`, `docker rm`)
5. Persist or clean data (`docker volume ...`)

## 3) Dockerfile Theory Using This Project

Source file: `27.1-docker-compose-example/DockerFile`

### Current file

```dockerfile
FROM oven/bun:1-alpine

WORKDIR /app

# Install dependencies first (better Docker cache reuse)
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile

# Copy application source
COPY prisma ./prisma
COPY prisma.config.ts ./
COPY src ./src
COPY tsconfig.json ./

# Generate Prisma client at build time
RUN bunx prisma generate

EXPOSE 3000

# Apply migrations on startup, then run API
CMD ["sh", "-c", "bunx prisma migrate deploy && bun src/index.ts"]
```

### Why each block exists

- `FROM oven/bun:1-alpine`: lightweight Bun runtime base.
- `WORKDIR /app`: all following operations happen in `/app`.
- `COPY package.json bun.lock` + `bun install`: dependency layer isolated for cache reuse.
- `COPY prisma/prisma.config.ts/src/tsconfig.json`: includes app + schema + TS config.
- `RUN bunx prisma generate`: ensures Prisma client exists in image.
- `EXPOSE 3000`: documents app port.
- `CMD ... migrate deploy && run`: applies committed migrations at startup, then starts API.

### Build cache strategy (important)

Copying dependency files before source code avoids reinstalling packages on every code change.

If only `src/index.ts` changes, Docker can reuse cached dependency layers and rebuild faster.

## 5) Volume, Network, and Persistence Theory

### Volumes

Postgres writes data to `/var/lib/postgresql/data` inside container.  
Compose maps that path to Docker volume `pg-users-data`.

Result:

- Remove container -> data still exists.
- Recreate container with same volume -> data returns.

### Networking and hostnames

With Compose, services are on an internal network automatically.

- App reaches DB at hostname `postgres` (service name), not `localhost`.
- `localhost` inside app container means "that same app container", not host machine.

### `host.docker.internal` vs service DNS

- Use `postgres` when both containers run in same Docker network (recommended).
- Use `host.docker.internal` when container must call a service running on host.

## Volume Concept (MongoDB `/data/db`) - from your diagram

Your diagram shows a very important Docker concept:

- You have a MongoDB container
- MongoDB stores data inside the container path: `/data/db`
- That path is mounted to a Docker volume on your Mac host
- If container is deleted, data still remains in the volume

### Why this is needed

Without volume:

- MongoDB writes inside container writable layer
- `docker rm` deletes container
- database data is lost

With volume:

- MongoDB writes to `/data/db`
- `/data/db` is linked to a persistent Docker volume
- container can be recreated, data stays safe

### Mental model

```text
Mac Host
┌──────────────────────────────┐
│ Docker Volume: mongo-data    │
└───────────────┬──────────────┘
                │ mounted to
                ▼
MongoDB Container
┌──────────────────────────────┐
│ /data/db  (Mongo files)      │
└──────────────────────────────┘
```

### Docker Compose example

```yaml
services:
  mongo:
    image: mongo:7
    container_name: mongo
    ports:
      - "27017:27017"
    volumes:
      - mongo-data:/data/db

volumes:
  mongo-data:
```

### Equivalent docker run command

```bash
docker volume create mongo-data

docker run -d \
  --name mongo \
  -p 27017:27017 \
  -v mongo-data:/data/db \
  mongo:7
```

### Quick test to prove persistence

1. Insert some data in MongoDB.
2. Remove container: `docker rm -f mongo`
3. Start new container with same mount: `-v mongo-data:/data/db`
4. Check data again -> data is still there.

This is exactly the persistence behavior shown in your image.

## Example from class/repo screenshot (dev compose file)

```yaml
services:
  mongo:
    image: mongo:5.0
    volumes:
      - dbdata:/data/db

  app:
    build:
      context: ./
      dockerfile: Dockerfile
      target: development
    environment:
      - MONGO_URL=mongodb://mongo:27017/p5js-web-editor
    volumes:
      - .:/usr/src/app
      - /usr/src/app/node_modules
    ports:
      - "8000:8000"
      - "8002:8002"
    depends_on:
      - mongo

volumes:
  dbdata:
```

### Explanation (line-by-line mindset)

- `mongo` service:
  - `image: mongo:5.0` -> runs MongoDB container using version 5.0.
  - `volumes: - dbdata:/data/db` -> persists Mongo data using named volume `dbdata`.

- `app` service:
  - `build.context: ./` -> build from current project folder.
  - `build.dockerfile: Dockerfile` -> use this Dockerfile.
  - `build.target: development` -> use `development` stage from a multi-stage Dockerfile.
  - `environment: MONGO_URL=...` -> app connects to Mongo using hostname `mongo` (service name DNS).
  - `volumes: - .:/usr/src/app` -> bind-mount local source code into container (great for live dev updates).
  - `volumes: - /usr/src/app/node_modules` -> keeps container's `node_modules` isolated so host mount does not break dependencies.
  - `ports: 8000:8000` and `8002:8002` -> exposes container ports to your Mac.
  - `depends_on: - mongo` -> starts `mongo` before `app` (startup order only, not readiness guarantee).

- top-level `volumes`:
  - `dbdata:` declares named volume used by Mongo service.

### Why this pattern is used in development

- Fast iteration: source code changes on host reflect in container immediately.
- Safe dependency handling: container keeps its own Linux-compatible `node_modules`.
- Data persistence: Mongo records survive container recreation.

### Important improvement for reliability

`depends_on` does not wait for Mongo to be fully ready. For robust startup, add a Mongo healthcheck and use condition-based dependency in Compose.

## Quick Note: `Dockerfile` vs `docker-compose.yml`

Both are important, but they solve different problems.

### What a `Dockerfile` does

A `Dockerfile` is a **recipe to build one image**.

- Defines base image (`FROM node:22-alpine`)
- Copies files (`COPY`)
- Installs dependencies (`RUN npm ci`)
- Sets startup command (`CMD`)

In short: **Dockerfile tells Docker how to create a container image**.

### What `docker-compose.yml` does

A `docker-compose.yml` is an **orchestration file for multiple containers**.

- Defines services (`app`, `mongo`, `redis`, etc.)
- Connects them on networks
- Mounts volumes
- Sets environment variables and ports
- Controls startup order (`depends_on`)

In short: **Compose tells Docker how to run and connect containers together**.

### Main differences

| Topic | `Dockerfile` | `docker-compose.yml` |
| --- | --- | --- |
| Purpose | Build an image | Run/manage multi-container app |
| Scope | Usually one service image | Whole project stack |
| Used by | `docker build` | `docker compose up` |
| Defines | Build steps | Runtime wiring/config |
| Output | Docker image | Running services/containers |

### How they work together

For a typical app:

1. `Dockerfile` builds your app image.
2. `docker-compose.yml` starts that app image + database + other services.
3. Compose can build from Dockerfile automatically using:

```yaml
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile
```

So a simple way to remember is:

- `Dockerfile` = **how to pack one service**
- `docker-compose.yml` = **how to run the full system**

Now start API and call `GET /users` again -> previous records remain.

### API summary for interview revision

- `GET /health` -> DB connectivity check
- `GET /users` -> list all users
- `POST /users` -> create user (`username` required, unique)
- `DELETE /users/:id` -> delete user by id

### Common beginner mistakes

- Using wrong `DATABASE_URL` host/port
- Forgetting to run migration before starting API
- Not sending JSON header in POST request
- Trying to delete with wrong user id

## How app container connects to Postgres (network explanation)

Great question: are they connected via Docker network, or something else?

### Current setup (what we ran)

In current commands, app uses:

```env
DATABASE_URL=postgresql://postgres:postgres@host.docker.internal:5432/usersdb?schema=public
```

This means:

- Postgres container publishes port `5432` to your host (`-p 5432:5432`)
- App container calls `host.docker.internal:5432`
- `host.docker.internal` is a special DNS name that points from container -> host machine (Docker Desktop feature)

So in this setup, connection path is:

```text
App container -> host.docker.internal:5432 (host) -> mapped to pg-users:5432
```

### Alternative (recommended for container-to-container)

Use a custom Docker network and connect app to Postgres by container name.

```bash
docker network create app-net

docker run -d \
  --name pg-users \
  --network app-net \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=usersdb \
  -v pg-users-data:/var/lib/postgresql/data \
  postgres:16-alpine

docker run -d \
  --name user-project-api \
  --network app-net \
  -p 3000:3000 \
  -e DATABASE_URL="postgresql://postgres:postgres@pg-users:5432/usersdb?schema=public" \
  -e PORT=3000 \
  user-project:test
```

In this networked setup:

- `pg-users` works as hostname (Docker DNS)
- You do not need to expose DB to host (`-p 5432:5432`) unless you want host access

### Which should you use?

- **Quick local learning:** `host.docker.internal` approach is easy.
- **Production-style container communication:** custom network + service/container name is better.
