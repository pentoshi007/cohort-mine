## 1. What is SSL/TLS?

**SSL (Secure Sockets Layer)** and its successor **TLS (Transport Layer Security)** are cryptographic protocols that provide secure communication over a computer network.

### Why do we need it?

```
Without SSL/TLS:
Browser -----> [ HTTP ] -----> Server
         (plain text, anyone can read)

With SSL/TLS:
Browser -----> [ HTTPS ] -----> Server
         (encrypted, no one can read in between)
```

- **Encryption** — Data between client and server is encrypted
- **Authentication** — Proves the server is who it claims to be
- **Data Integrity** — Ensures data hasn't been tampered with during transit

### How it works (simplified)

```
1. Client says "Hello" to server (Client Hello)
2. Server responds with its SSL certificate (Server Hello)
3. Client verifies the certificate with a Certificate Authority (CA)
4. Both agree on a shared encryption key (Key Exchange)
5. All further communication is encrypted with that key
```

This whole process is called the **TLS Handshake** and happens in milliseconds.

## 2. What is Certbot?

**Certbot** is a free, open-source tool made by the **Electronic Frontier Foundation (EFF)** that automates:

- Obtaining SSL/TLS certificates from Let's Encrypt
- Configuring your web server (Nginx/Apache) to use them
- Automatically renewing certificates before they expire

### Why Certbot?

| Feature | Without Certbot | With Certbot |
|---------|----------------|--------------|
| Get certificate | Manual CSR generation, submit to CA, pay money | One command, free |
| Configure Nginx | Manually edit config files | Auto-configured |
| Renewal | Manual, easy to forget | Auto-renewal via cron/systemd |
| Cost | $10–$200+/year per domain | **Free** |

## 3. What is Let's Encrypt?

**Let's Encrypt** is a free, automated, and open **Certificate Authority (CA)**.

- Run by the **Internet Security Research Group (ISRG)**
- Provides **Domain Validated (DV)** certificates
- Certificates are valid for **90 days** (by design, to encourage automation)
- Trusted by all major browsers

### How Let's Encrypt Validates You Own a Domain

Let's Encrypt uses the **ACME protocol** (Automatic Certificate Management Environment) with challenges:

| Challenge Type | How it Works | Use Case |
|---------------|-------------|----------|
| **HTTP-01** | Places a file at `http://yourdomain/.well-known/acme-challenge/` and verifies it | Most common, works with Nginx/Apache |
| **DNS-01** | Creates a TXT record in your DNS | Required for wildcard certs |
| **TLS-ALPN-01** | Validates via TLS on port 443 | Less common |

## 4. Prerequisites

Before starting, you need:

1. **A server** (Ubuntu 20.04/22.04/24.04 recommended) with root/sudo access
2. **A domain name** pointing to your server's IP address
3. **Nginx installed** and running
4. **Ports 80 and 443 open** in your firewall

### Verify your setup

```bash
# Check if Nginx is installed and running
sudo systemctl status nginx

# Check if ports are open
sudo ufw status

# If not, allow them
sudo ufw allow 'Nginx Full'   # allows both 80 and 443
sudo ufw enable

# Verify your domain points to your server
dig +short yourdomain.com
# Should show your server's IP address
```

### DNS Setup

In your domain registrar (GoDaddy, Namecheap, Cloudflare, etc.), create:

```
Type: A
Name: @              (or yourdomain.com)
Value: YOUR_SERVER_IP
TTL: 300

Type: A
Name: www
Value: YOUR_SERVER_IP
TTL: 300
```

Wait for DNS propagation (can take a few minutes to 48 hours, usually ~5 minutes).

## 5. Step 1 — Install Certbot

### Modern Method: Using Snap (Recommended by Certbot)

The Certbot team now recommends installing via **snap** instead of `apt` because snap provides the latest version.

```bash
# Step 1: Make sure snapd is installed and up to date
sudo snap install core
sudo snap refresh core

# Step 2: Remove any old OS-packaged Certbot (avoids conflicts)
sudo apt remove certbot       # removes old apt version if any

# Step 3: Install Certbot via snap
sudo snap install --classic certbot

# Step 4: Create a symlink so you can use 'certbot' directly
sudo ln -s /snap/bin/certbot /usr/bin/certbot

# Step 5: Verify installation
certbot --version
# Output: certbot 2.x.x (or newer)
```

#### Why snap over apt?

- `apt` repositories often have **outdated** Certbot versions
- `snap` always gives you the **latest** Certbot
- `snap` auto-updates itself
- Certbot's official docs now **only support snap** installation

### Alternative: Using pip (for advanced users)

```bash
sudo python3 -m venv /opt/certbot/
sudo /opt/certbot/bin/pip install --upgrade pip
sudo /opt/certbot/bin/pip install certbot certbot-nginx
sudo ln -s /opt/certbot/bin/certbot /usr/bin/certbot
```

## 6. Step 2 — Basic Nginx Configuration

Before running Certbot, you need a basic Nginx server block for your domain.

### Create a server block

```bash
sudo nano /etc/nginx/sites-available/yourdomain.com
```

Add this basic HTTP config:

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name yourdomain.com www.yourdomain.com;

    # Root directory for your site
    root /var/www/yourdomain.com/html;
    index index.html index.htm;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

### If you're reverse-proxying a Node.js/Express app:

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name yourdomain.com www.yourdomain.com;

    location / {
        proxy_pass http://localhost:3000;      # Your app's port
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
    }
}
```

### Enable the site

```bash
# Create a symlink to enable the site
sudo ln -s /etc/nginx/sites-available/yourdomain.com /etc/nginx/sites-enabled/

# Test the Nginx configuration for syntax errors
sudo nginx -t
# Output should say: syntax is ok, test is successful

# Reload Nginx to apply changes
sudo systemctl reload nginx
```

### Verify it's working

```bash
# Visit in browser or use curl
curl http://yourdomain.com
# Should return your site content (or the proxied app's response)
```

## 7. Step 3 — Obtain an SSL Certificate

Now the main event — getting the SSL certificate.

### Method 1: Let Certbot auto-configure Nginx (Recommended)

```bash
sudo certbot --nginx -d yourdomain.com -d www.yourdomain.com
```

**What this command does:**

1. Contacts Let's Encrypt servers
2. Performs the HTTP-01 challenge (proves you own the domain)
3. Downloads the certificate files
4. **Automatically modifies** your Nginx config to use SSL
5. Sets up HTTP → HTTPS redirect

**Interactive prompts:**

```
Enter email address: your@email.com           # For renewal reminders
Agree to Terms of Service: Y
Share email with EFF: N (optional)
```

**On success, you'll see:**

```
Successfully received certificate.
Certificate is saved at: /etc/letsencrypt/live/yourdomain.com/fullchain.pem
Key is saved at:         /etc/letsencrypt/live/yourdomain.com/privkey.pem
```

### Method 2: Obtain certificate only (manual Nginx config)

If you want full control over your Nginx config:

```bash
sudo certbot certonly --nginx -d yourdomain.com -d www.yourdomain.com
```

The `certonly` flag means: "Just get the certificate, don't touch my Nginx config." You'll then need to manually configure Nginx to use the certs (covered later).

### Method 3: Standalone mode (when Nginx isn't running)

```bash
# Stop Nginx temporarily
sudo systemctl stop nginx

# Get the cert (Certbot runs its own web server on port 80)
sudo certbot certonly --standalone -d yourdomain.com -d www.yourdomain.com

# Start Nginx again
sudo systemctl start nginx
```

### Method 4: Webroot mode (Nginx already serving files)

```bash
sudo certbot certonly --webroot -w /var/www/yourdomain.com/html -d yourdomain.com -d www.yourdomain.com
```

This places challenge files in your webroot directory without stopping Nginx.

## 8. Step 4 — Understanding What Certbot Did

### Certificate files location

All certificates are stored in `/etc/letsencrypt/live/yourdomain.com/`:

```
/etc/letsencrypt/live/yourdomain.com/
├── fullchain.pem    → Your certificate + intermediate CA cert (send to clients)
├── privkey.pem      → Your private key (NEVER share this)
├── cert.pem         → Your certificate only
└── chain.pem        → Intermediate CA certificate only
```

| File | What it is | Used for |
|------|-----------|----------|
| `fullchain.pem` | Your cert + Let's Encrypt intermediate cert | `ssl_certificate` in Nginx |
| `privkey.pem` | Your private key | `ssl_certificate_key` in Nginx |
| `cert.pem` | Your certificate alone | Rarely used directly |
| `chain.pem` | Intermediate cert alone | Rarely used directly |

### What Certbot added to your Nginx config

After running `certbot --nginx`, your config now looks something like:

```nginx
server {
    server_name yourdomain.com www.yourdomain.com;

    root /var/www/yourdomain.com/html;
    index index.html index.htm;

    location / {
        try_files $uri $uri/ =404;
    }

    # ---- Everything below was added by Certbot ----

    listen [::]:443 ssl;    # IPv6 + SSL
    listen 443 ssl;          # IPv4 + SSL

    ssl_certificate /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;        # Recommended SSL settings
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;          # Diffie-Hellman params
}

# ---- Certbot also adds this redirect block ----
server {
    if ($host = www.yourdomain.com) {
        return 301 https://$host$request_uri;
    }

    if ($host = yourdomain.com) {
        return 301 https://$host$request_uri;
    }

    listen 80;
    listen [::]:80;

    server_name yourdomain.com www.yourdomain.com;
    return 404;
}
```

### What's inside `options-ssl-nginx.conf`?

```bash
cat /etc/letsencrypt/options-ssl-nginx.conf
```

```nginx
ssl_session_cache shared:le_nginx_SSL:10m;
ssl_session_timeout 1440m;
ssl_session_tickets off;

ssl_protocols TLSv1.2 TLSv1.3;
ssl_prefer_server_ciphers off;

ssl_ciphers "ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384";
```

Key points:
- **TLSv1.2 and TLSv1.3 only** — older TLS 1.0/1.1 are disabled (insecure)
- **Strong cipher suites** — only modern, secure ciphers
- **Session caching** — improves performance for repeat visitors

## 9. Step 5 — Auto-Renewal

Let's Encrypt certificates expire every **90 days**. Certbot sets up auto-renewal automatically.

### How auto-renewal works

When installed via snap, Certbot creates a **systemd timer** that runs twice daily:

```bash
# Check if the timer is active
sudo systemctl status snap.certbot.renew.timer

# Or list all timers
sudo systemctl list-timers | grep certbot
```

Output:

```
NEXT                         LEFT          LAST                         PASSED    UNIT                      ACTIVATES
Mon 2026-02-09 06:27:00 UTC  1 day 12h     Sat 2026-02-07 18:27:00 UTC 3h ago    snap.certbot.renew.timer  snap.certbot.renew.service
```

### How renewal actually works

```
Every ~12 hours:
  1. Certbot checks ALL certificates
  2. If a cert expires within 30 days → renew it
  3. If renewed → reload Nginx automatically
  4. If not expiring soon → do nothing
```

### Test renewal (dry run)

```bash
sudo certbot renew --dry-run
```

This simulates the renewal process without actually renewing. If it succeeds, you're good.

**Expected output:**

```
Saving debug log to /var/log/letsencrypt/letsencrypt.log
- - - - - - - - - - - - - - - - - - - - - - - - - - - - -
Processing /etc/letsencrypt/renewal/yourdomain.com.conf
- - - - - - - - - - - - - - - - - - - - - - - - - - - - -
Simulating renewal of an existing certificate for yourdomain.com and www.yourdomain.com
- - - - - - - - - - - - - - - - - - - - - - - - - - - - -
Congratulations, all simulated renewals succeeded:
  /etc/letsencrypt/live/yourdomain.com/fullchain.pem (success)
```

### Add a post-renewal hook (to reload Nginx)

Certbot via snap already handles this, but if you need a custom hook:

```bash
# Create a deploy hook
sudo nano /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

```bash
#!/bin/bash
systemctl reload nginx
```

```bash
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
```

### Hook directories explained

```
/etc/letsencrypt/renewal-hooks/
├── pre/       → Scripts that run BEFORE renewal attempt
├── deploy/    → Scripts that run AFTER successful renewal
└── post/      → Scripts that run AFTER renewal attempt (success or failure)
```

## 10. Wildcard Certificates

A **wildcard certificate** covers `*.yourdomain.com` — meaning it secures ALL subdomains:

- `api.yourdomain.com`
- `app.yourdomain.com`
- `admin.yourdomain.com`
- Any other subdomain

### Getting a wildcard certificate

Wildcard certs **require DNS-01 challenge** (not HTTP-01):

```bash
sudo certbot certonly \
  --manual \
  --preferred-challenges dns \
  -d "yourdomain.com" \
  -d "*.yourdomain.com"
```

**What happens:**

1. Certbot asks you to create a DNS TXT record:

```
Please deploy a DNS TXT record under the name:
_acme-challenge.yourdomain.com

with the following value:
aB3dEf4gH5iJkLmN6oPqRsT7uVwXyZ1234567890
```

2. You go to your DNS provider and create:

```
Type: TXT
Name: _acme-challenge
Value: aB3dEf4gH5iJkLmN6oPqRsT7uVwXyZ1234567890
TTL: 300
```

3. Wait for propagation, then press Enter in the terminal.

4. Certbot verifies the TXT record and issues the wildcard cert.

### Automating wildcard renewal with DNS plugins

Manual DNS challenges are painful for renewal. Use a **DNS plugin** to automate it:

#### Example: Cloudflare DNS Plugin

```bash
# Install the Cloudflare plugin
sudo snap set certbot trust-plugin-with-root=ok
sudo snap install certbot-dns-cloudflare

# Create a credentials file
sudo mkdir -p /etc/letsencrypt/
sudo nano /etc/letsencrypt/cloudflare.ini
```

```ini
# Cloudflare API Token (recommended — scoped to DNS edit for your zone)
dns_cloudflare_api_token = YOUR_CLOUDFLARE_API_TOKEN
```

```bash
# Secure the credentials file
sudo chmod 600 /etc/letsencrypt/cloudflare.ini

# Get the wildcard cert with auto DNS validation
sudo certbot certonly \
  --dns-cloudflare \
  --dns-cloudflare-credentials /etc/letsencrypt/cloudflare.ini \
  -d "yourdomain.com" \
  -d "*.yourdomain.com"
```

Now renewals are **fully automatic** — Certbot will update DNS records itself.

#### Other DNS plugins available

| DNS Provider | Plugin Name |
|-------------|-------------|
| Cloudflare | `certbot-dns-cloudflare` |
| Route 53 (AWS) | `certbot-dns-route53` |
| Google Cloud DNS | `certbot-dns-google` |
| DigitalOcean | `certbot-dns-digitalocean` |
| Namecheap | `certbot-dns-namecheap` |

## 11. Multiple Domains

### Single certificate for multiple domains (SAN certificate)

```bash
sudo certbot --nginx \
  -d yourdomain.com \
  -d www.yourdomain.com \
  -d api.yourdomain.com \
  -d admin.yourdomain.com
```

All four domains will be on **one certificate**. This is called a **Subject Alternative Name (SAN)** certificate.

### Separate certificates for different domains

```bash
# Certificate 1
sudo certbot --nginx -d siteA.com -d www.siteA.com

# Certificate 2
sudo certbot --nginx -d siteB.com -d www.siteB.com
```

### List all certificates

```bash
sudo certbot certificates
```

Output:

```
Found the following certs:
  Certificate Name: yourdomain.com
    Domains: yourdomain.com www.yourdomain.com
    Expiry Date: 2026-05-08 (VALID: 89 days)
    Certificate Path: /etc/letsencrypt/live/yourdomain.com/fullchain.pem
    Private Key Path: /etc/letsencrypt/live/yourdomain.com/privkey.pem
```

### Expand an existing certificate (add more domains)

```bash
sudo certbot --nginx --expand -d yourdomain.com -d www.yourdomain.com -d new-subdomain.yourdomain.com
```

## 12. Manual DNS Challenge

Sometimes you can't use the HTTP challenge (e.g., server is behind a firewall, or you need a wildcard cert). In that case, you use the **DNS-01 challenge**.

### Step-by-step

```bash
sudo certbot certonly \
  --manual \
  --preferred-challenges dns \
  -d yourdomain.com
```

Certbot will output:

```
Please deploy a DNS TXT record under the name:
  _acme-challenge.yourdomain.com.
with the following value:
  randomStringHere123456

Before continuing, verify the TXT record has been deployed.
Press Enter to Continue
```

### Verify the TXT record

Before pressing Enter, verify:

```bash
# Check if the TXT record has propagated
dig TXT _acme-challenge.yourdomain.com +short

# Should show:
# "randomStringHere123456"

# Alternative: use nslookup
nslookup -type=TXT _acme-challenge.yourdomain.com
```

Only press Enter once the TXT record is visible.

## 13. Revoking & Deleting Certificates

### Revoke a certificate

Revocation tells Let's Encrypt the certificate is no longer valid:

```bash
# Revoke by certificate name
sudo certbot revoke --cert-name yourdomain.com

# Or revoke by certificate path
sudo certbot revoke --cert-path /etc/letsencrypt/live/yourdomain.com/fullchain.pem
```

### Delete a certificate

After revoking, clean up the files:

```bash
sudo certbot delete --cert-name yourdomain.com
```

### When to revoke?

- Private key was compromised
- You no longer own the domain
- You're decommissioning a server

## 14. Troubleshooting

### Common errors and fixes

#### Error: "Could not automatically find a matching server block"

**Cause:** Nginx config doesn't have a `server_name` matching your domain.

**Fix:**
```bash
# Make sure your server block has the correct server_name
server_name yourdomain.com www.yourdomain.com;

# Test and reload
sudo nginx -t && sudo systemctl reload nginx
```

#### Error: "Challenge failed — connection refused"

**Cause:** Port 80 is blocked by a firewall.

**Fix:**
```bash
sudo ufw allow 80
sudo ufw allow 443
sudo ufw reload
```

#### Error: "Too many requests / rate limited"

**Cause:** Let's Encrypt has rate limits:
- 50 certificates per registered domain per week
- 5 duplicate certificates per week
- 5 failed validations per hour

**Fix:** Use `--staging` for testing:

```bash
# Use the staging server (no rate limits, but certs won't be trusted)
sudo certbot --nginx --staging -d yourdomain.com

# Once everything works, remove --staging and run again
sudo certbot --nginx -d yourdomain.com
```

#### Error: "Unable to find a virtual host"

**Cause:** Site not enabled in Nginx.

**Fix:**
```bash
# Make sure the symlink exists
ls -la /etc/nginx/sites-enabled/

# If missing, create it
sudo ln -s /etc/nginx/sites-available/yourdomain.com /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

#### Error: "Nginx test failed"

```bash
# Check what's wrong
sudo nginx -t

# Common fix: check for duplicate listen directives or missing semicolons
sudo nano /etc/nginx/sites-available/yourdomain.com
```

### Debug logs

```bash
# Certbot logs are here
sudo cat /var/log/letsencrypt/letsencrypt.log

# Last 50 lines
sudo tail -50 /var/log/letsencrypt/letsencrypt.log
```

## 15. Full Production Nginx + SSL Config

Here's a complete, production-ready Nginx configuration with SSL:

```nginx
# ============================================================
# HTTP → HTTPS Redirect
# ============================================================
server {
    listen 80;
    listen [::]:80;

    server_name yourdomain.com www.yourdomain.com;

    # Redirect ALL HTTP requests to HTTPS
    return 301 https://$host$request_uri;
}

# ============================================================
# www → non-www Redirect (optional — pick one canonical URL)
# ============================================================
server {
    listen 443 ssl;
    listen [::]:443 ssl;

    server_name www.yourdomain.com;

    ssl_certificate /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;

    return 301 https://yourdomain.com$request_uri;
}

# ============================================================
# Main HTTPS Server Block
# ============================================================
server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;                    # Enable HTTP/2 (Nginx 1.25.1+ syntax)

    server_name yourdomain.com;

    # ----- SSL Certificate -----
    ssl_certificate /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;

    # ----- HSTS (HTTP Strict Transport Security) -----
    # Tells browsers to ALWAYS use HTTPS for the next 1 year
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;

    # ----- Security Headers -----
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-XSS-Protection "1; mode=block" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    # ----- OCSP Stapling -----
    # Speeds up TLS handshake by stapling OCSP response
    ssl_stapling on;
    ssl_stapling_verify on;
    resolver 8.8.8.8 8.8.4.4 valid=300s;
    resolver_timeout 5s;

    # ----- Logging -----
    access_log /var/log/nginx/yourdomain.com.access.log;
    error_log /var/log/nginx/yourdomain.com.error.log;

    # ----- Proxy to your application -----
    location / {
        proxy_pass http://localhost:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;

        # Timeouts
        proxy_connect_timeout 60s;
        proxy_send_timeout 60s;
        proxy_read_timeout 60s;
    }

    # ----- Static assets caching -----
    location ~* \.(jpg|jpeg|png|gif|ico|css|js|svg|woff|woff2|ttf|eot)$ {
        proxy_pass http://localhost:3000;
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # ----- Block access to hidden files -----
    location ~ /\. {
        deny all;
        access_log off;
        log_not_found off;
    }
}
```

### Understanding each section

| Section | Purpose |
|---------|---------|
| HTTP → HTTPS redirect | Forces all traffic to use encryption |
| www → non-www redirect | Canonical URL for SEO |
| `http2 on` | HTTP/2 for faster page loads (multiplexing, header compression) |
| HSTS header | Browsers remember to always use HTTPS |
| Security headers | Prevent clickjacking, MIME sniffing, XSS |
| OCSP Stapling | Faster TLS handshake |
| Proxy settings | Forward requests to your Node.js/Express app |
| Static asset caching | Browser caches assets for 30 days |
| Block hidden files | Prevent `.env`, `.git` access |

### Test the SSL configuration

After setting everything up:

```bash
# Test Nginx config
sudo nginx -t

# Reload Nginx
sudo systemctl reload nginx

# Test SSL from command line
curl -I https://yourdomain.com

# Check SSL grade (use an external tool)
# Visit: https://www.ssllabs.com/ssltest/analyze.html?d=yourdomain.com
```

### Complete workflow at a glance

```
1. Buy/get a domain → Point DNS A record to your server IP
2. Install Nginx     → sudo apt install nginx
3. Configure Nginx   → Create server block with server_name
4. Install Certbot   → sudo snap install --classic certbot
5. Get certificate   → sudo certbot --nginx -d yourdomain.com
6. Verify HTTPS      → Visit https://yourdomain.com
7. Test renewal      → sudo certbot renew --dry-run
8. Done! Auto-renewal is already set up.
```

### Key commands cheat sheet

| Task | Command |
|------|---------|
| Install Certbot | `sudo snap install --classic certbot` |
| Get cert + auto-config | `sudo certbot --nginx -d domain.com` |
| Get cert only | `sudo certbot certonly --nginx -d domain.com` |
| Wildcard cert | `sudo certbot certonly --manual --preferred-challenges dns -d "*.domain.com"` |
| List all certs | `sudo certbot certificates` |
| Test renewal | `sudo certbot renew --dry-run` |
| Force renewal | `sudo certbot renew --force-renewal` |
| Revoke cert | `sudo certbot revoke --cert-name domain.com` |
| Delete cert | `sudo certbot delete --cert-name domain.com` |
| Check Nginx config | `sudo nginx -t` |
| Reload Nginx | `sudo systemctl reload nginx` |
| View renewal timer | `sudo systemctl list-timers \| grep certbot` |
| Check cert expiry | `echo \| openssl s_client -connect domain.com:443 2>/dev/null \| openssl x509 -noout -dates` |

### Important things to remember

1. **Let's Encrypt certs last 90 days** — auto-renewal handles this
2. **Always use `--staging` for testing** — avoids rate limits
3. **Wildcard certs need DNS challenge** — HTTP challenge won't work
4. **Keep `privkey.pem` secret** — never commit it to Git
5. **Test with `nginx -t` before reloading** — prevents downtime
6. **Check SSL grade** at ssllabs.com — aim for A+
7. **HSTS preload** — once enabled, hard to undo (browsers cache it)
