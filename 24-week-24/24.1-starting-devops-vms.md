# Special Network Addresses in IP Networking

## Reserved Addresses

### Loopback Address: `127.0.0.1`

- Used for internal communication within the same device
- Traffic sent here never leaves the machine
- Commonly used for testing network software locally

### Link-Local Addresses: `169.254.x.x`

- Automatically assigned when a device cannot obtain an IP from DHCP
- Only valid for communication within the same network segment
- Range: `169.254.0.0` to `169.254.255.255`

---

## Broadcast Addresses

In networking, broadcast addresses are used when a device needs to communicate with **all devices** rather than a specific destination. They differ based on which layer of the network they target and how routers handle them.

### 1. Layer 2 Broadcast: `FF:FF:FF:FF:FF:FF`

| Property  | Details                             |
| --------- | ----------------------------------- |
| **Type**  | MAC Address                         |
| **Layer** | Data Link Layer (Layer 2)           |
| **Scope** | Local segment (same switch or VLAN) |

**When it's sent:** Every time a device needs to send a frame to all other devices on the same physical segment.

**Common Use Case:** ARP Requests — When your computer knows an IP address (like `192.168.1.5`) but doesn't know the hardware MAC address needed to send data, it sends an ARP request to `FF:FF:FF:FF:FF:FF`.

**Router Behavior:** Routers **discard** these. They do not forward Layer 2 broadcasts to other networks.

---

### 2. Limited Broadcast: `255.255.255.255`

| Property  | Details                   |
| --------- | ------------------------- |
| **Type**  | IP Address                |
| **Layer** | Network Layer (Layer 3)   |
| **Scope** | Current local subnet only |

**When it's sent:** When a device doesn't yet know its own IP address or the structure of the local network.

**Common Use Case:** DHCP Discovery — When a computer first connects to a network and asks "Is there a DHCP server here that can give me an IP?", it sends a packet to `255.255.255.255`.

**Router Behavior:** Routers **always discard** these by default to prevent broadcast traffic from flooding the entire internet.

---

### 3. Directed Broadcast: `<network-address>.255`

| Property  | Details                                                               |
| --------- | --------------------------------------------------------------------- |
| **Type**  | Subnet-specific broadcast (e.g., `192.168.1.255` for a `/24` network) |
| **Layer** | Network Layer (Layer 3)                                               |
| **Scope** | Specific subnet                                                       |

**When it's sent:** When you want to reach every device within a specific subnet, even if you are not currently in that subnet.

**Common Use Case:** Older service discovery protocols like NetBIOS or diagnostic tools (like a "broadcast ping").

**Router Behavior:**

- **Local:** If sent from within the subnet, it acts like a normal broadcast.
- **Remote:** If sent from a different network, routers _can_ technically route it to the target network. However, most modern routers **discard directed broadcasts by default** to prevent security risks like Smurf attacks.

---

## Comparison Table

| Address Type       | Address Format      | Network Layer  | Scope              | Forwarded by Router?          |
| ------------------ | ------------------- | -------------- | ------------------ | ----------------------------- |
| Layer 2 Broadcast  | `FF:FF:FF:FF:FF:FF` | Data Link (L2) | Local Segment Only | ❌ No                         |
| Limited Broadcast  | `255.255.255.255`   | Network (L3)   | Local Subnet Only  | ❌ No                         |
| Directed Broadcast | `192.168.1.255`     | Network (L3)   | Specific Subnet    | ⚠️ Usually No (Security risk) |

---

## Key Takeaways

1. **Layer 2 broadcasts** (`FF:FF:FF:FF:FF:FF`) are for hardware-level discovery within a single segment
2. **Limited broadcasts** (`255.255.255.255`) are for network-level discovery when you don't know your network configuration
3. **Directed broadcasts** (`x.x.x.255`) target a specific subnet but are typically blocked for security
4. **Routers act as broadcast boundaries** — they don't forward broadcast traffic between networks

# Hardware → Hypervisor → OS → VMs (AWS Context)

When you run a **VM** (e.g. an EC2 instance) in the cloud, it sits on a stack of layers. Understanding this stack helps with security, performance, and troubleshooting.

## The Stack (Bottom to Top)

```
┌─────────────────────────────────────┐
│  VMs (Guest OS) — e.g. your EC2     │  ← What you see and manage
├─────────────────────────────────────┤
│  Host OS (Dom0 / minimal host)       │  ← AWS-controlled, you never see it
├─────────────────────────────────────┤
│  Hypervisor                         │  ← Creates and isolates VMs
├─────────────────────────────────────┤
│  Physical Hardware (servers, NICs)   │  ← AWS data center
└─────────────────────────────────────┘
```

---

## 1. Hardware (Physical Layer)

- **What it is:** Real servers in AWS data centers — CPUs, RAM, disks, network cards (NICs), GPUs (for some instance types).
- **In AWS:** You never touch this. AWS owns and maintains the hardware. When you pick an instance type (e.g. `t3.medium`, `m5.large`), you get a **slice** of that hardware allocated to your VM.
- **Why it matters:** Instance types map to different hardware generations and capabilities (vCPU, memory, network bandwidth, local NVMe). The hypervisor is what turns one physical machine into many logical ones.

---

## 2. Hypervisor

- **What it is:** Software (or hardware-assisted software) that **creates and runs virtual machines**. It sits between the hardware and the guest OSes. It:
  - Schedules CPU and memory across multiple VMs.
  - Virtualizes devices (disk, network) so each VM sees its own “hardware.”
  - Enforces isolation so one VM cannot access another’s memory or resources.
- **In AWS:**
  - **Nitro System** (most current instances): Custom hypervisor + dedicated Nitro cards for storage, networking, and management. Much of the virtualization is offloaded to hardware, which improves performance and security and reduces the “surface” of software you must trust.
  - **Xen** (older/legacy): AWS used Xen hypervisor for many years; some older instance types still use it. The host OS (Dom0) runs on top of Xen and manages the guests.
- **Why it matters:** The hypervisor is the boundary that makes your VM a VM. In AWS, you don’t manage it; they do. Nitro’s design (minimal software on the host, hardware offload) is a big part of why modern EC2 instances have good performance and strong isolation.

---

## 3. Host OS (Dom0 / Control Plane OS)

- **What it is:** The first OS that boots on the physical machine, running **on top of** the hypervisor. It hosts the management tools that create VMs, attach storage, configure networking, and handle monitoring. In Xen terminology this is often called **Dom0** (domain 0).
- **In AWS:** This OS is fully controlled by AWS. You never log into it or patch it. It is kept minimal (especially with Nitro) to reduce attack surface. Your EC2 instance is a **guest** (e.g. DomU in Xen terms), not the host.
- **Why it matters:** Anything running in the host OS could theoretically see or affect all VMs on that box. AWS’s responsibility is to harden and isolate this layer so your VM is safe. You only interact with your **guest** OS inside the VM.

---

## 4. VMs (Guest OS / Your EC2 Instances)

- **What it is:** The actual virtual machine — CPU, RAM, virtual disks, and a **guest operating system** (Linux, Windows, etc.) that you install or that comes from an AMI. This is your EC2 instance from the console/CLI.
- **In AWS:** Each EC2 instance is one VM. You choose the AMI (which includes the OS), instance type (hardware profile), storage (EBS, instance store), and networking (VPC, security groups). The hypervisor and host OS make it look like a dedicated machine, but it’s virtualized on shared hardware.
- **Why it matters:** This is the only layer you manage (OS updates, apps, config). Understanding that it runs inside a VM on a hypervisor on real hardware helps you reason about:
  - **Performance:** Noisy neighbors, burstable vs fixed performance, and instance types.
  - **Security:** Your responsibility (guest OS + apps) vs AWS’s (hypervisor, host OS, physical security).
  - **Networking:** Virtual NICs and VPC are presented to the guest by the hypervisor/Nitro.

---

## Summary Table (AWS)

| Layer          | What it is                            | Who manages it                      | You interact?                   |
| -------------- | ------------------------------------- | ----------------------------------- | ------------------------------- |
| **Hardware**   | Physical servers, NICs, storage       | AWS                                 | No (indirect via instance type) |
| **Hypervisor** | Nitro / Xen; creates and isolates VMs | AWS                                 | No                              |
| **Host OS**    | Dom0 / minimal control-plane OS       | AWS                                 | No                              |
| **VMs**        | Your EC2 instances (guest OS + apps)  | You (+ AWS for underlying platform) | Yes (SSH, AMI, config)          |

---

## Key Takeaways

1. **Hardware** = physical servers in AWS data centers; you get a virtual slice via instance types.
2. **Hypervisor** = Nitro (or Xen) creates and isolates VMs; you don’t manage it.
3. **Host OS** = AWS’s management OS (e.g. Dom0); you never see or manage it.
4. **VMs** = your EC2 instances; this is the only layer you configure and maintain (OS, apps, security patches).
5. Understanding this stack clarifies **shared responsibility**: AWS secures and operates hardware, hypervisor, and host OS; you secure and operate everything inside your VMs.

# SSH (Secure Shell): In-Depth Concepts and Steps

SSH secures remote access to servers (e.g. your EC2 VMs). For **cyber** work it underpins secure access and hardening; for **web dev** it’s how you deploy, debug, and automate access to production. Below is how each feature works and how to use it in practice.

## Key Features of SSH (Overview)

1. **Encryption** — Data between client and server is encrypted so interceptors cannot read it.
2. **Authentication** — Server verifies who you are (password or public key).
3. **Integrity** — Data cannot be altered in transit without breaking the connection.

---

## 1. Encryption (In Depth)

### Why It Matters

- **Telnet / FTP** send credentials and data in **plaintext**. Anyone on the path (Wi‑Fi, ISP, attacker) can read them.
- **SSH** encrypts the entire session: login, commands, and output. Interception yields ciphertext only.

### How It Works (Conceptually)

1. **Key exchange (e.g. Diffie–Hellman)**  
   Client and server agree on a **shared secret** over the wire without ever sending that secret directly. An eavesdropper sees only the public parameters, not the resulting key.

2. **Session key**  
   That shared secret is used to derive a **symmetric session key** (e.g. AES). Symmetric crypto is fast and used for the bulk of the traffic.

3. **Algorithms**  
   - **Key exchange:** `curve25519-sha256`, `ecdh-sha2-nistp256`, or classic `diffie-hellman-group14-sha256`.  
   - **Cipher:** e.g. `aes256-gcm@openssh.com`, `chacha20-poly1305@openssh.com`.  
   - **Server host key:** identifies the server (e.g. `ed25519`, `ecdsa`, or `rsa`).

4. **What you see**  
   On first connect you get “host key fingerprint.” That fingerprint is a hash of the server’s public key. You verify it once (out-of-band or via a trusted source) so later you can detect **host key change** (possible MITM).

**Cyber angle:** Prefer modern algorithms (Ed25519, ChaCha20-Poly1305) and disable weak ciphers/KEX in `sshd_config` to reduce attack surface.  
**Web dev angle:** Encryption is automatic; focus on verifying the host key the first time and on keeping client/server SSH up to date.

---

## 2. Authentication (In Depth)

Two main methods: **password-based** and **public key–based**. Public key is preferred for both security and automation.

### 2a. Password-Based Authentication

**Flow:**

1. Client sends username.
2. Server challenges for password (over the **already encrypted** channel).
3. Client sends password; server checks it against `/etc/shadow` (or equivalent).
4. If it matches, server grants a shell (or runs the requested command).

**Pros:** Simple, no key setup.  
**Cons:** Weak to brute force, phishing, and reuse; cannot easily automate without exposing the password.

**When to use:** Initial setup of a new VM when you don’t have keys on it yet. Many guides (e.g. DigitalOcean) say: “While setting up a server, select password-based authentication” so you can log in once, then add keys and optionally disable passwords.

**Steps (typical Linux VM, e.g. EC2 or DigitalOcean):**

1. Create VM; note its IP and the initial user (e.g. `ubuntu`, `root`, or `ec2-user`).
2. Ensure `sshd_config` allows password auth (for that first login):
   - `PasswordAuthentication yes`
   - Restart SSH: `systemctl restart sshd` (or `ssh`).
3. Log in: `ssh user@<server-ip>`, enter password when prompted.
4. After adding public key auth (below), you can set `PasswordAuthentication no` and restart SSH for better security.

---

### 2b. Public Key–Based Authentication (In Depth)

**Why it’s “a more secure method”:**

- No password travels over the wire; no password to phish or brute force at the server.
- Private key stays on your machine (or in an agent); only the **public** key is on the server.
- Enables **automation**: scripts, CI/CD, and `ssh` without typing a password (e.g. deployments to EC2).

**Concepts:**

- **Key pair:**  
  - **Private key** (e.g. `~/.ssh/id_ed25519`): must stay secret; used to **prove** you own the corresponding public key.  
  - **Public key** (e.g. `~/.ssh/id_ed25519.pub`): can be shared; stored on the server in `~/.ssh/authorized_keys`.

- **Challenge–response:**  
  Server sends a challenge (derived from the public key and random data). Only the holder of the private key can compute the correct response. So “the client uses a **private key** to authenticate; the server checks this against the **corresponding public key**.”

**Steps (end-to-end):**

**Step 1 — Generate a key pair (on your laptop / dev machine):**

```bash
ssh-keygen -t ed25519 -C "your_email@example.com" -f ~/.ssh/id_ed25519
```

- `-t ed25519`: use Ed25519 (recommended; short and secure).  
- `-f`: path; default is `~/.ssh/id_ed25519` (or `id_rsa` for RSA).  
- Optionally set a **passphrase** so the key file alone is not enough (recommended for cyber/dev machines).

**Step 2 — Copy the public key to the server:**

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@<server-ip>
```

- This appends your public key to `user@server:~/.ssh/authorized_keys`.  
- You’ll need **password** auth once for this; after that you can use the key.

**Manual alternative (if `ssh-copy-id` isn’t available):**

```bash
cat ~/.ssh/id_ed25519.pub
# Copy the line, then on the server:
mkdir -p ~/.ssh
echo "paste-the-public-key-line" >> ~/.ssh/authorized_keys
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

**Step 3 — Connect with the key:**

```bash
ssh -i ~/.ssh/id_ed25519 user@<server-ip>
```

If the key is in the default name (`id_ed25519` or `id_rsa`), you can just:

```bash
ssh user@<server-ip>
```

**Step 4 (optional) — Disable password auth after keys work:**

On the server, in `/etc/ssh/sshd_config`:

- `PasswordAuthentication no`  
- `PermitRootLogin prohibit-password` (or `no` if you don’t need root SSH)

Then: `systemctl restart sshd`. Now only key-based logins are allowed — “eliminates the need for passwords and provides an extra layer of security.”

**AWS EC2 specifics:**

- EC2 uses **key pairs** (PEM files). You don’t run `ssh-keygen` for the instance; AWS (or you) created the pair at launch.
- Connect: `ssh -i /path/to/your-key.pem ec2-user@<public-ip>` (Amazon Linux) or `ubuntu@<public-ip>` (Ubuntu AMI).
- To use your **own** key (e.g. for CI/CD): add your **public** key to `~/.ssh/authorized_keys` on the instance (once, via the PEM login), then you can use your normal key or automation with that key.

**Cyber angle:** Harden `authorized_keys` (no stray keys), use strong key types (Ed25519/ECDSA), protect private keys with passphrases and minimal file permissions (`chmod 600`).  
**Web dev angle:** Use the same key (or a deploy key) in CI/CD to `ssh` into staging/production for deploys or health checks without storing passwords.

---

## 3. Integrity (In Depth)

**What it means:** Data in transit cannot be **tampered with** without the connection failing. So “if someone tries to alter the data being sent, the connection will be immediately disrupted.”

**How it works:**

- SSH uses a **Message Authentication Code (MAC)** or an **Authenticated Encryption (AE)** scheme (e.g. AES-GCM, ChaCha20-Poly1305).
- For each packet, the sender computes a tag from the ciphertext (and often sequence number) using a key derived from the session. The receiver recomputes the tag; if it doesn’t match, the packet is rejected and the connection is torn down.
- So: **encryption** hides content; **integrity** ensures that any change (by a MITM or corruption) is detected and the session is not silently compromised.

**Why it matters:**

- Without integrity, an attacker could flip bits in encrypted data and possibly change commands or responses (e.g. “rm” vs “ls”).
- With integrity, tampering breaks the connection, so you don’t trust altered data.

**Cyber angle:** Prefer AE ciphers (e.g. `aes256-gcm@openssh.com`, `chacha20-poly1305@openssh.com`) so encryption and integrity are tied together.  
**Web dev angle:** Default OpenSSH config usually enables good MACs/ciphers; keep SSH updated so you get integrity and strong crypto by default.

---

## Summary Table (SSH Features)

| Feature        | What it does                         | Cyber focus                          | Web dev focus                          |
| -------------- | ------------------------------------ | ------------------------------------ | -------------------------------------- |
| **Encryption** | Encrypts all traffic                 | Strong ciphers/KEX; disable weak     | Verify host key; keep SSH updated      |
| **Auth (pwd)** | Server checks password               | Use only for initial setup           | First login, then add keys              |
| **Auth (key)** | Client proves identity with key pair | Harden keys; passphrase; minimal perms | Deploy keys, CI/CD without passwords   |
| **Integrity**  | Detects tampering; drops connection  | Prefer AE ciphers                    | Rely on defaults; update OpenSSH       |

---

## Practical Checklist (VM / EC2 / Droplet)

1. **First time:** Use password auth if needed to get in, or use the cloud’s key (e.g. EC2 PEM).
2. **Generate key:** `ssh-keygen -t ed25519`; keep private key secure and passphrase-protected.
3. **Install key:** `ssh-copy-id user@host` or manually add to `~/.ssh/authorized_keys`.
4. **Test:** `ssh user@host` (or `ssh -i key.pem user@host` on EC2).
5. **Harden:** Set `PasswordAuthentication no` (and optionally `PermitRootLogin prohibit-password`), restart `sshd`.
6. **Automation:** Use the same key (or a dedicated deploy key) in scripts/CI for secure, passwordless access to your VMs.
