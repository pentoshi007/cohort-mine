## What is Docker?

Docker is a platform for developing, shipping, and running applications inside **containers**. Containers are lightweight, isolated environments that package an application with all its dependencies, libraries, and configuration files.

Think of it this way:

> You zip your app + its entire environment into a single box. That box runs the same way on **any** machine — your laptop, your coworker's laptop, a CI server, or a production server in AWS.

### Key Terms at a Glance

| Term | What It Means |
|------|--------------|
| **Image** | A read-only template/blueprint containing your app + its environment |
| **Container** | A running instance of an image — the actual process |
| **Dockerfile** | A text file with instructions to build an image |
| **Docker Hub** | A cloud registry to store and share images (like GitHub for Docker images) |
| **Docker Compose** | A tool to define and run multi-container apps with a YAML file |
| **Volume** | Persistent storage that survives container restarts |
| **Registry** | A server that stores Docker images (Docker Hub, AWS ECR, GCR, etc.) |

## Why Docker?

### The "It Works on My Machine" Problem

Without Docker, you often encounter situations where:

- Code works on your laptop but fails on a colleague's machine
- Development environment differs from staging/production
- Different projects require different versions of Node.js, Python, databases, etc.
- Setting up a new developer takes hours or days
- "But I have Node 16 installed and this project needs Node 20..."

### What Issues Docker Solves

1. **Environment Consistency**: The same container runs identically everywhere — your laptop, CI/CD, staging, and production

2. **Dependency Isolation**: Each project has its own isolated environment. No more conflicting versions of Node.js, Python, or system libraries

3. **Easy Onboarding**: New developers run `docker compose up` and have a fully working environment in minutes

4. **Reproducible Builds**: If it builds in a container, it will build the same way every time

5. **Simplified Deployment**: Package your app once, deploy anywhere that runs Docker

6. **Infrastructure as Code**: Define your entire stack (app, database, cache, etc.) in a `docker-compose.yml` file

7. **Microservices Friendly**: Each service runs in its own container, independently scalable

### Docker vs Virtual Machines

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      VIRTUAL MACHINES                                    │
│                                                                          │

│  ├──────────┤   ├──────────┤   ├──────────┤                            │
│  │ Guest OS │   │ Guest OS │   │ Guest OS │  ← Each VM has FULL OS    │
│  └──────────┘   └──────────┘   └──────────┘                            │
│  ┌──────────────────────────────────────────┐                           │
│  │             Hypervisor                    │                           │
│  ├──────────────────────────────────────────┤                           │
│  │             Host OS                       │                           │
│  ├──────────────────────────────────────────┤                           │
│  │             Hardware                      │                           │
│  └──────────────────────────────────────────┘                           │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│                        DOCKER CONTAINERS                                 │
│                                                                          │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐                            │
│  │  App A   │   │  App B   │   │  App C   │                            │
│  ├──────────┤   ├──────────┤   ├──────────┤                            │

│  ├──────────────────────────────────────────┤                           │
│  │             Host OS                       │                           │

```

| Feature | Docker Containers | Virtual Machines |
|---------|-------------------|-----------------|
| Startup time | Seconds | Minutes |
| Resource usage | Lightweight (shares OS kernel) | Heavy (full OS per VM) |
| Isolation | Process-level | Hardware-level |
| Portability | Very high | Lower |
| Image size | MBs (50-500 MB typical) | GBs (2-20 GB typical) |
| Performance | Near-native | Overhead from hypervisor |

**Bottom line**: Use Docker for app deployment. Use VMs when you need complete OS isolation (e.g., running Windows on a Linux host).

## Docker Architecture — How It Works Under the Hood

Understanding the architecture helps you debug problems and make better decisions.

```
┌──────────────────────────────────────────────────────────────────────┐
│                         YOUR MACHINE                                  │
│                                                                       │
│  ┌──────────────┐         ┌──────────────────────────────────────┐   │
│  │  Docker CLI  │ ──────► │         Docker Daemon (dockerd)      │   │
│  │  (client)    │  REST   │                                      │   │
│  │              │  API    │  ┌─────────┐ ┌─────────┐ ┌────────┐ │   │
│  │ docker build │         │  │Container│ │Container│ │ Image  │ │   │
│  │ docker run   │         │  │ Manager │ │ Runtime │ │ Store  │ │   │
│  │ docker push  │         │  └─────────┘ └─────────┘ └────────┘ │   │
│  └──────────────┘         └──────────────────────────────────────┘   │
│                                        │                              │
│                                        ▼                              │
│                            ┌───────────────────┐                      │
│                            │  Docker Registry   │                     │
│                            │  (Docker Hub, ECR, │                     │
│                            │   GCR, ACR, etc.)  │                     │
│                            └───────────────────┘                      │
└──────────────────────────────────────────────────────────────────────┘
```

### The Three Key Components

| Component | Role | Example |
|-----------|------|---------|
| **Docker Client (CLI)** | You type commands here | `docker run`, `docker build` |
| **Docker Daemon** | Background process that manages images, containers, networks, volumes | `dockerd` running on your machine |
| **Docker Registry** | Remote storage for images | Docker Hub, AWS ECR, GitHub Container Registry |

### How a `docker run` Works Step by Step

```
You type: docker run -d -p 3000:3000 node:18-alpine

1. CLI sends request to Docker Daemon via REST API
2. Daemon checks: "Do I have node:18-alpine locally?"
   ├── YES → Use local image
   └── NO  → Pull from Docker Hub (docker.io/library/node:18-alpine)
3. Daemon creates a new container from the image
4. Daemon allocates a writable filesystem layer on top of image layers
5. Daemon creates a network interface and assigns an IP
6. Daemon sets up port mapping (host 3000 → container 3000)
7. Daemon starts the container process
8. Container is now running!
```

## Docker Images vs Containers

This is the most fundamental concept. Get this right and everything else clicks.

### Key Distinction

- **Docker Image** = Blueprint / Template (like a **class** in OOP)
- **Docker Container** = Running instance of an image (like an **object** in OOP)

### Visual Explanation

```
┌─────────────────────────────────────────────────────────────┐
│                    DOCKER IMAGE                              │
│                                                              │
│  A read-only template containing:                           │
│  - Base OS (e.g., Ubuntu, Alpine)                           │
│  - Application code                                         │
│  - Dependencies & libraries                                 │
│  - Environment variables & configurations                   │
│  - Commands to run on startup                               │
│                                                              │
│  Size: Typically 50MB - 2GB                                 │
│  Status: Static (doesn't change once built)                 │
│  Storage: On disk (in Docker registry or local)             │
└─────────────────────────────────────────────────────────────┘
                            |
              (docker run my-image:latest)
                            |
                            v
┌─────────────────────────────────────────────────────────────┐
│                    DOCKER CONTAINER                          │
│                                                              │
│  A running instance with:                                   │
│  - All contents from the image (read-only layer)            │
│  - Writable layer for runtime changes                       │
│  - Isolated filesystem, networking, processes               │
│  - Resources (CPU, memory) allocated                        │
│  - Can be started, stopped, restarted                       │
│                                                              │
│  Status: Dynamic (changes as it runs)                       │
│  Storage: In memory + Docker storage driver                 │
│  Lifespan: Temporary (deleted when stopped, unless saved)   │
└─────────────────────────────────────────────────────────────┘
```

### One Image → Many Containers

```
                    ┌──────────────────┐
                    │  nginx:latest    │
                    │     IMAGE        │
                    └──────────────────┘
                            │
           ┌────────────────┼────────────────┐
           │                │                │
           v                v                v
    ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
    │ Container 1 │  │ Container 2 │  │ Container 3 │
    │ Port: 8001  │  │ Port: 8002  │  │ Port: 8003  │
    │ Running     │  │ Running     │  │ Stopped     │
    └─────────────┘  └─────────────┘  └─────────────┘
```

### Key Differences Summary

| Aspect | Image | Container |
|--------|-------|-----------|
| **Mutability** | Immutable (read-only) | Mutable (writable layer on top) |
| **Persistence** | Persists until deleted | Deleted when removed (by default) |
| **Purpose** | Template / Distribution | Execution / Runtime |
| **Analogy** | Recipe | The dish cooked from the recipe |
| **Lifecycle** | Build → Tag → Push | Create → Run → Stop → Remove |

### Layering Concept

Docker images use a **layered filesystem**. Each instruction in a Dockerfile creates a new layer. Layers are cached and reused, making builds fast.

```
┌─────────────────────────────────────────┐
│   Writable Layer (Container)            │  ← Changes made at runtime
├─────────────────────────────────────────┤
│   Application Layer (COPY . .)          │  ← Your app code
├─────────────────────────────────────────┤
│   Dependencies Layer (RUN npm install)  │  ← npm, pip packages, etc.
├─────────────────────────────────────────┤
│   OS/Base Layer (FROM node:18-alpine)   │  ← Ubuntu, Alpine, etc.
└─────────────────────────────────────────┘
```

Each layer is read-only and **reusable** across different images, which makes Docker efficient in terms of storage and build times.

**Why this matters**: If you change only your app code, Docker rebuilds only the top layer and reuses the cached dependency layer. This is why the order of instructions in a Dockerfile matters for build speed.

## Dockerfile — The Blueprint

A Dockerfile is a plain text file that contains a series of instructions telling Docker how to build your image. Every line is an instruction.

### Complete Dockerfile Instruction Reference

#### `FROM` — Base Image

Every Dockerfile starts here. It defines the base image your app builds on top of.

```dockerfile
FROM node:18-alpine          # Node.js 18 on Alpine Linux (lightweight)
FROM python:3.11-slim        # Python 3.11 on Debian slim
FROM ubuntu:22.04            # Full Ubuntu
FROM golang:1.21             # Go 1.21
FROM scratch                 # Empty image (for Go binaries, etc.)
```

**Choosing a base image**:
- Use `-alpine` variants for smallest size (~5 MB base)
- Use `-slim` variants for a balance of size and compatibility
- Use full images only when you need specific system libraries
- Always pin a version — **never** use `latest` in production

```
node:18         → ~900 MB  (full Debian + Node)
node:18-slim    → ~200 MB  (Debian slim + Node)
node:18-alpine  → ~120 MB  (Alpine Linux + Node)
```

---

#### `WORKDIR` — Set Working Directory

Sets the directory for all subsequent commands. Creates it if it doesn't exist.

```dockerfile
WORKDIR /app

# All following commands run inside /app
# COPY, RUN, CMD, etc. are relative to /app
```

**Why not `RUN cd /app`?** Because `cd` only affects the current `RUN` layer. `WORKDIR` persists across all subsequent instructions.

---

#### `COPY` vs `ADD` — Copy Files into Image

```dockerfile
# COPY — simple, predictable (preferred)
COPY package.json ./             # Copy single file
COPY package*.json ./            # Copy matching files (package.json + package-lock.json)
COPY . .                         # Copy everything from build context to WORKDIR
COPY src/ ./src/                 # Copy a directory

# ADD — same as COPY but with extras (avoid unless needed)
ADD https://example.com/file.tar.gz /app/   # Can download URLs
ADD archive.tar.gz /app/                     # Auto-extracts tar archives
```

**Rule of thumb**: Always use `COPY` unless you specifically need URL download or tar extraction.

---

#### `RUN` — Execute Commands During Build

Runs a command inside the image during the build process. Each `RUN` creates a new layer.

```dockerfile
# Install dependencies
RUN npm install

# Install system packages
RUN apt-get update && apt-get install -y curl

# Create directories
RUN mkdir -p /app/logs

# Chain commands to reduce layers (best practice)
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl git && \
    rm -rf /var/lib/apt/lists/*
```

**Tip**: Chain related commands with `&&` and `\` to reduce the number of layers and image size.

---

#### `CMD` vs `ENTRYPOINT` — What Runs When Container Starts

This is a common source of confusion. Here's the difference:

```dockerfile
# CMD — default command (can be overridden by user)
CMD ["npm", "start"]
# When user runs: docker run my-app
# Executes: npm start
# When user runs: docker run my-app node server.js
# Executes: node server.js (CMD is overridden!)

# ENTRYPOINT — fixed command (cannot be easily overridden)
ENTRYPOINT ["node"]
CMD ["app.js"]
# When user runs: docker run my-app
# Executes: node app.js
# When user runs: docker run my-app server.js
# Executes: node server.js (only the CMD part is overridden)
```

| Feature | `CMD` | `ENTRYPOINT` |
|---------|-------|-------------|
| Purpose | Default command/arguments | Fixed executable |
| Override | Fully replaced by `docker run` args | Args appended, not replaced |
| Common use | App startup command | When container should always run one program |
| Multiple | Only last CMD takes effect | Only last ENTRYPOINT takes effect |

**For most backend apps**: Just use `CMD ["npm", "start"]` or `CMD ["node", "server.js"]`.

**Exec form vs Shell form**:
```dockerfile
# Exec form (preferred) — runs directly, receives signals properly
CMD ["npm", "start"]

# Shell form — runs inside /bin/sh -c, may not handle signals well
CMD npm start
```

Always use exec form (`["command", "arg1", "arg2"]`) in production.

---

#### `EXPOSE` — Document a Port

`EXPOSE` is **documentation only**. It tells people reading the Dockerfile which port the app listens on. It does NOT actually publish the port.

```dockerfile
EXPOSE 3000
EXPOSE 5432
EXPOSE 8080/tcp
EXPOSE 8080/udp
```

You still need `-p` in `docker run` to actually map the port.

---

#### `ENV` vs `ARG` — Variables

```dockerfile
# ENV — available at build time AND runtime (inside running container)
ENV NODE_ENV=production
ENV PORT=3000

# ARG — available ONLY at build time (not in running container)
ARG NODE_VERSION=18
FROM node:${NODE_VERSION}-alpine

ARG BUILD_DATE
LABEL build-date=$BUILD_DATE
```

```bash
# Pass ARG values at build time
docker build --build-arg NODE_VERSION=20 --build-arg BUILD_DATE=$(date) -t my-app .
```

| Feature | `ENV` | `ARG` |
|---------|-------|-------|
| Available during build | Yes | Yes |
| Available at runtime | Yes | No |
| Set from CLI | `docker run -e` | `docker build --build-arg` |
| Persisted in image | Yes | No |

---

#### `LABEL` — Metadata

```dockerfile
LABEL maintainer="your-email@example.com"
LABEL version="1.0"
LABEL description="Express API server"
```

---

#### `USER` — Run as Non-Root

```dockerfile
# Create a non-root user
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

# Switch to that user
USER appuser

# All subsequent commands (and the container itself) run as appuser
```

**Why**: Running as root inside a container is a security risk. If someone breaks into the container, they have root access. Always run as non-root in production.

---

#### `HEALTHCHECK` — Container Health Monitoring

```dockerfile
HEALTHCHECK --interval=30s --timeout=10s --start-period=40s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1
```

| Option | Meaning | Default |
|--------|---------|---------|
| `--interval` | Time between checks | 30s |
| `--timeout` | Max time for a single check | 30s |
| `--start-period` | Grace period for container startup | 0s |
| `--retries` | Consecutive failures before "unhealthy" | 3 |

Docker uses this to report container status as `healthy`, `unhealthy`, or `starting`.

### Putting It All Together — Anatomy of a Real Dockerfile

```dockerfile
# 1. Start from a base image
FROM node:18-alpine

# 2. Add metadata
LABEL maintainer="you@example.com"
LABEL description="Production Express API"

# 3. Set working directory
WORKDIR /app

# 4. Copy dependency files first (for better caching)
COPY package.json package-lock.json ./

# 5. Install dependencies
RUN npm ci --only=production

# 6. Copy application code
COPY . .

# 7. Create non-root user
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

# 8. Document the port
EXPOSE 3000

# 9. Health check
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/health || exit 1

# 10. Default command
CMD ["node", "server.js"]
```

## Building Your First Docker Image

### Step 1: Create a Simple App

```bash
mkdir my-docker-app && cd my-docker-app
```

Create `server.js`:

```javascript
const http = require('http');

const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({
    message: 'Hello from Docker!',
    hostname: require('os').hostname(),
    uptime: process.uptime()
  }));
});

server.listen(3000, () => {
  console.log('Server running on port 3000');
});
```

Create `Dockerfile`:

```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY server.js .
EXPOSE 3000
CMD ["node", "server.js"]
```

### Step 2: Build the Image

```bash
docker build -t my-first-app:1.0 .
#            │        │          │
#            │        │          └─ Build context (current directory)
#            │        └─ Image name:tag
#            └─ Flag to tag the image
```

**What happens during build**:

```
Step 1/5 : FROM node:18-alpine
 ---> Pulling from library/node (if not cached)
Step 2/5 : WORKDIR /app
 ---> Running in abc123def
Step 3/5 : COPY server.js .
 ---> Copying file
Step 4/5 : EXPOSE 3000
 ---> Documentation layer
Step 5/5 : CMD ["node", "server.js"]
 ---> Setting default command
Successfully built 7a8b9c0d1e2f
Successfully tagged my-first-app:1.0
```

### Step 3: Verify

```bash
# List your images
docker images

# Output:
# REPOSITORY      TAG    IMAGE ID       CREATED          SIZE
# my-first-app    1.0    7a8b9c0d1e2f   10 seconds ago   180MB
```

### Build Options You'll Use Often

```bash
# Build with no cache (fresh build from scratch)
docker build --no-cache -t my-app:1.0 .

# Build with a specific Dockerfile
docker build -f Dockerfile.prod -t my-app:prod .

# Build with build arguments
docker build --build-arg NODE_ENV=production -t my-app:1.0 .

# Build with multiple tags
docker build -t my-app:1.0 -t my-app:latest .

# Build and see full output (no build kit collapsing)
DOCKER_BUILDKIT=0 docker build -t my-app:1.0 .
```

## Running Containers

### Basic `docker run`

```bash
# Run in foreground (you'll see logs, Ctrl+C to stop)
docker run my-first-app:1.0

# Run in background (detached mode) — most common
docker run -d my-first-app:1.0

# Run with a custom name
docker run -d --name my-app my-first-app:1.0

# Run with port mapping
docker run -d --name my-app -p 3000:3000 my-first-app:1.0

# Run and auto-remove when stopped (great for testing)
docker run --rm -p 3000:3000 my-first-app:1.0

# Run interactively (for debugging or exploring)
docker run -it node:18-alpine /bin/sh
```

### The `-d` Flag (Detached Mode)

Without `-d`, the container runs in the foreground and your terminal is locked to it. With `-d`, it runs in the background and returns the container ID.

```bash
docker run -d --name web -p 3000:3000 my-first-app:1.0
# Output: a1b2c3d4e5f6...  (container ID)

# Now check it's running
docker ps
```

### Container Lifecycle

```
docker run ──► CREATED ──► RUNNING ──► STOPPED ──► REMOVED
                             │            │
                     docker stop      docker start
                     docker kill      (restart)
                             │
                       docker rm (permanent delete)
```

### Managing Running Containers

```bash
# List running containers
docker ps

# List ALL containers (running + stopped)
docker ps -a

# Stop a container (sends SIGTERM, then SIGKILL after 10s)
docker stop my-app

# Kill a container immediately (sends SIGKILL)
docker kill my-app

# Start a stopped container
docker start my-app

# Restart a running container
docker restart my-app

# Remove a stopped container
docker rm my-app

# Force remove a running container
docker rm -f my-app

# Remove all stopped containers
docker container prune
```

### Viewing Logs

```bash
# View all logs
docker logs my-app

# Follow logs in real-time (like tail -f)
docker logs -f my-app

# Show last 50 lines
docker logs --tail 50 my-app

# Show logs with timestamps
docker logs -t my-app

# Show logs since a specific time
docker logs --since 2025-01-01T00:00:00 my-app
docker logs --since 10m my-app     # Last 10 minutes
```

### Executing Commands Inside a Running Container

```bash
# Open an interactive shell
docker exec -it my-app /bin/sh        # Alpine/lightweight images
docker exec -it my-app /bin/bash      # Debian/Ubuntu images

# Run a specific command
docker exec my-app ls -la /app
docker exec my-app cat /app/package.json
docker exec my-app env                 # View environment variables
docker exec my-app node -v             # Check Node.js version

# The -it flags:
# -i = interactive (keep STDIN open)
# -t = allocate a pseudo-TTY (terminal)
```

## Port Mapping

### Why Port Mapping is Necessary

Containers are **isolated by design**. When you run an application inside a container (like a web server on port 3000), that port is only accessible inside the container, not from your host machine.

```
WITHOUT port mapping:
┌──────────────────────┐
│  Container           │
│  App on port 3000    │     Your browser: localhost:3000
└──────────────────────┘     ❌ Connection refused!

WITH port mapping (-p 8080:3000):
┌──────────────────────┐
│  Container           │     Your browser: localhost:8080
│  App on port 3000    │ ◄── ✅ Works!
└──────────────────────┘
```

### Syntax

```bash
docker run -p HOST_PORT:CONTAINER_PORT IMAGE

#           ─────┬──── ──────┬────────
#                │           │
#    Port on YOUR machine    Port INSIDE the container
```

### Common Examples

```bash
# Web app: access at localhost:8080, app runs on container port 3000
docker run -p 8080:3000 my-web-app

# Same port mapping (most common for databases)
docker run -p 5432:5432 postgres:14
docker run -p 27017:27017 mongo:latest
docker run -p 6379:6379 redis:7

# Multiple ports
docker run -p 3000:3000 -p 9229:9229 my-app    # App + debugger

# Map to localhost only (more secure, not accessible from network)
docker run -p 127.0.0.1:3000:3000 my-app

# Let Docker pick a random host port
docker run -p 3000 my-app    # Docker assigns a random host port
docker port my-app           # Check what port was assigned
```

### Visual Flow

```
Step 1: You send HTTP request
┌──────────────────────────────────────┐
│ Browser: http://localhost:8080       │
└──────────────────────────────────────┘
              |
              v
Step 2: Docker routes to container
┌──────────────────────────────────────┐
│ Docker Port Mapper: 8080 → 3000     │
└──────────────────────────────────────┘
              |
              v
Step 3: Container receives request
┌──────────────────────────────────────┐
│ Container App listening on port 3000 │
│ ✅ Request successfully routed!      │
└──────────────────────────────────────┘
```

### Viewing Port Mappings

```bash
# See port mappings in docker ps output
docker ps
# PORTS column shows: 0.0.0.0:8080->3000/tcp

# Get detailed port info for a container
docker port my-app
# Output: 3000/tcp -> 0.0.0.0:8080
```

### Troubleshooting Port Issues

| Problem | Cause | Solution |
|---------|-------|----------|
| "Address already in use" | Host port is occupied | Use different host port: `-p 9090:3000` |
| Can't connect to localhost:8080 | Port not mapped | Add `-p` flag when running container |
| App works in container but not from host | Wrong port mapped | Check app listens on `CONTAINER_PORT` |
| Can't connect from other machine | Bound to localhost only | Use `-p 0.0.0.0:8080:3000` |

## Volumes & Persistent Data

### The Problem

Containers are **ephemeral** — when you remove a container, all data inside it is lost. This is a problem for databases, file uploads, logs, etc.

```bash
# Data is lost when container is removed!
docker run -d --name my-db postgres:14
docker exec my-db psql -U postgres -c "CREATE TABLE users (id int);"
docker rm -f my-db                    # Database data is gone forever!
```

### The Solution: Volumes

Volumes allow data to persist outside the container and survive container removal.

### Three Types of Mounts

```
┌─────────────────────────────────────────────────────────────┐
│                     HOST MACHINE                             │
│                                                              │
│  1. Named Volume          2. Bind Mount       3. tmpfs      │
│  ┌────────────────┐     ┌────────────────┐   (in memory)   │
│  │ /var/lib/docker │     │ /your/project  │                 │
│  │ /volumes/data   │     │ /src           │                 │
│  └───────┬────────┘     └───────┬────────┘                 │
│          │                      │                           │
│          ▼                      ▼                           │
│  ┌──────────────────────────────────────┐                   │
│  │           CONTAINER                   │                   │
│  │   /app/data      /app/src             │                   │
│  └──────────────────────────────────────┘                   │
└─────────────────────────────────────────────────────────────┘
```

### 1. Named Volumes (Recommended for Production)

Docker manages the storage location. Best for databases and persistent data.

```bash
# Create a named volume
docker volume create my-data

# Use a named volume
docker run -d --name my-db \
  -v my-data:/var/lib/postgresql/data \
  postgres:14

# Volume persists even after container is removed
docker rm -f my-db
# Data is still in my-data volume!

# Start a new container with the same volume
docker run -d --name my-db-2 \
  -v my-data:/var/lib/postgresql/data \
  postgres:14
# All data is still there!

# List volumes
docker volume ls

# Inspect a volume (see where it's stored on host)
docker volume inspect my-data

# Remove a volume
docker volume rm my-data

# Remove all unused volumes
docker volume prune
```

### 2. Bind Mounts (Best for Development)

Maps a specific directory on your host to a directory in the container. Great for live development — you edit code on your host and it's instantly reflected in the container.

```bash
# Mount current directory into container
docker run -d --name dev-app \
  -v $(pwd):/app \
  -p 3000:3000 \
  node:18-alpine npm start

# Changes you make to files on your host are immediately
# visible inside the container (and vice versa)

# Mount with read-only access (container can't modify host files)
docker run -d \
  -v $(pwd)/config:/app/config:ro \
  my-app
```

### 3. tmpfs Mount (In-Memory, Temporary)

Data stored in host memory. Useful for secrets or temporary data that should never be written to disk.

```bash
docker run -d --tmpfs /app/tmp my-app
```

### Common Volume Patterns

```bash
# Database persistence
docker run -d --name postgres \
  -v postgres-data:/var/lib/postgresql/data \
  -p 5432:5432 \
  postgres:14

# MongoDB persistence
docker run -d --name mongo \
  -v mongo-data:/data/db \
  -p 27017:27017 \
  mongo:latest

# Redis persistence
docker run -d --name redis \
  -v redis-data:/data \
  -p 6379:6379 \
  redis:7 redis-server --appendonly yes

# Development with hot-reload
docker run -d --name dev \
  -v $(pwd):/app \
  -v /app/node_modules \
  -p 3000:3000 \
  my-app npm run dev

# Note: -v /app/node_modules creates an anonymous volume
# to prevent host node_modules from overwriting container's
```

### Volume in Docker Compose

```yaml
services:
  db:
    image: postgres:14
    volumes:
      - postgres-data:/var/lib/postgresql/data    # Named volume
      - ./init.sql:/docker-entrypoint-initdb.d/   # Bind mount

  app:
    build: .
    volumes:
      - .:/app              # Bind mount (development)
      - /app/node_modules   # Anonymous volume (preserve container's node_modules)

volumes:
  postgres-data:            # Declare named volumes here
```

### Passing Environment Variables

```bash
# Method 1: Inline with -e
docker run -e NODE_ENV=production -e PORT=3000 my-app

# Method 2: From a .env file
docker run --env-file .env my-app

# Method 3: From host environment
export MY_SECRET=abc123
docker run -e MY_SECRET my-app    # Passes host's MY_SECRET value
```

### In Dockerfile

```dockerfile
# Set defaults (can be overridden at runtime)

ENV PORT=3000
```

### In Docker Compose

```yaml
services:
  app:
    build: .
    environment:
      - NODE_ENV=production
      - DATABASE_URL=postgres://user:pass@db:5432/mydb
    # OR from a file:
    env_file:
      - .env
      - .env.production
```

### Secrets Management (Don't Hardcode Passwords!)

**Never do this**:

```dockerfile
# BAD — password is baked into the image forever!
ENV DATABASE_PASSWORD=supersecret123
```

**Do this instead**:

```bash
# Pass secrets at runtime via -e or --env-file
docker run --env-file .env.production my-app

# Or use Docker secrets (for Docker Swarm)
echo "supersecret" | docker secret create db_password -
```

**In Docker Compose** (using `.env` file):

```yaml
# docker-compose.yml
services:
  app:
    build: .
    env_file:
      - .env    # .env file contains secrets, not committed to git
```

```bash
# .env (add to .gitignore!)
DATABASE_URL=postgres://user:realpassword@db:5432/mydb
JWT_SECRET=your-real-jwt-secret
API_KEY=sk-1234567890
```

## Docker Networking

### How Containers Communicate

By default, containers are isolated. Docker provides networking to let containers talk to each other.

### Default Networks

```bash
# List networks
docker network ls

# You'll see three default networks:
# bridge   — Default for standalone containers
# host     — Container shares host's network (no isolation)
# none     — No networking at all
```

### Creating a Custom Network (Recommended)

```bash
# Create a custom bridge network
docker network create my-network

# Run containers on the same network
docker run -d --name api --network my-network my-api
docker run -d --name db --network my-network postgres:14

# Now 'api' can reach 'db' using the container name as hostname!
# Inside the api container: postgres://user:pass@db:5432/mydb
#                                                  ^^
#                                         Container name = hostname
```

### Why Custom Networks?

| Feature | Default Bridge | Custom Network |
|---------|---------------|----------------|
| Container name DNS | No (must use IP) | Yes (`db`, `api`, etc.) |
| Isolation | All containers share one bridge | Only containers on same network see each other |
| Hot connect/disconnect | No | Yes |

### Docker Compose Networking (Automatic!)

Docker Compose creates a network automatically. All services can reach each other **by service name**.

```yaml
services:
  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      - DATABASE_URL=postgres://user:pass@db:5432/mydb
      #                                    ^^
      #                          Service name = hostname

  db:
    image: postgres:14
    environment:
      POSTGRES_PASSWORD: pass
```

In the above example, the `api` service can connect to `db:5432` because Docker Compose sets up DNS resolution between services on the same network.

### Network Diagram

```
┌─────────────────────────────────────────────────────────────┐
│               Docker Compose Network                         │
│                  (app-network)                                │
│                                                              │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐   │
│  │   api        │    │   db         │    │   redis      │   │
│  │  :3000       │───►│  :5432       │    │  :6379       │   │
│  │              │    │              │    │              │   │
│  │              │────────────────────────►│              │   │
│  └──────┬───────┘    └──────────────┘    └──────────────┘   │
│         │                                                    │
└─────────┼────────────────────────────────────────────────────┘
          │ -p 3000:3000
          ▼
    Host: localhost:3000  ← Only the api is exposed to the host
```

Notice: `db` and `redis` don't need `-p` flags because they only need to be reachable by other containers, not from the host.

## Docker Compose — Multi-Container Apps

### What is Docker Compose?

Docker Compose lets you define and run **multi-container applications** using a single YAML file. Instead of running multiple `docker run` commands, you write one `docker-compose.yml` and run `docker compose up`.

### The `docker-compose.yml` Structure

```yaml
# docker-compose.yml

services:
  # Service 1: Your application
  app:
    build: .                          # Build from Dockerfile in current dir
    container_name: my-app
    ports:
      - "3000:3000"
    environment:
      - NODE_ENV=production
      - DATABASE_URL=postgres://user:password@db:5432/mydb
      - REDIS_URL=redis://redis:6379
    depends_on:
      - db
      - redis
    volumes:
      - .:/app                        # Bind mount for development
      - /app/node_modules             # Preserve container's node_modules
    restart: unless-stopped
    networks:
      - app-network

  # Service 2: PostgreSQL Database
  db:
    image: postgres:14-alpine
    container_name: my-db
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: password
      POSTGRES_DB: mydb
    ports:
      - "5432:5432"                   # Expose to host (for debugging)
    volumes:
      - postgres-data:/var/lib/postgresql/data
    restart: unless-stopped
    networks:
      - app-network

  # Service 3: Redis Cache
  redis:
    image: redis:7-alpine
    container_name: my-redis
    ports:
      - "6379:6379"
    volumes:
      - redis-data:/data
    restart: unless-stopped
    networks:
      - app-network

# Named volumes (data persists across container restarts)
volumes:
  postgres-data:
  redis-data:

# Custom network
networks:
  app-network:
    driver: bridge
```

### Docker Compose Commands

```bash
# Start all services (detached)
docker compose up -d

# Start and rebuild images
docker compose up -d --build

# Stop all services
docker compose down

# Stop and remove volumes (deletes database data!)
docker compose down -v

# View logs from all services
docker compose logs

# Follow logs from a specific service
docker compose logs -f app

# List running services
docker compose ps

# Execute command in a running service
docker compose exec app /bin/sh
docker compose exec db psql -U user -d mydb

# Restart a specific service
docker compose restart app

# Scale a service (run multiple instances)
docker compose up -d --scale app=3

# View resource usage
docker compose top
```

### The `depends_on` Caveat

`depends_on` only waits for the container to **start**, not for the service to be **ready**. A PostgreSQL container might start but take a few seconds to accept connections.

**Solution**: Use health checks in compose.

```yaml
services:
  db:
    image: postgres:14-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d mydb"]
      interval: 5s
      timeout: 5s
      retries: 5

  app:
    build: .
    depends_on:
      db:
        condition: service_healthy    # Wait until db is actually ready
```

### Development vs Production Compose Files

```bash
# docker-compose.yml — base config
# docker-compose.dev.yml — development overrides
# docker-compose.prod.yml — production overrides

# Development
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d

# Production
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

```yaml
# docker-compose.dev.yml
services:
  app:
    volumes:
      - .:/app                 # Live reload
    environment:
      - NODE_ENV=development
    command: npm run dev       # Use nodemon
```

```yaml
# docker-compose.prod.yml
services:
  app:
    environment:
      - NODE_ENV=production
    command: npm start
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: "0.5"
```

## Docker Hub — Push, Pull & Share Images

Docker Hub is the default public registry for Docker images. It's like GitHub but for container images.

### Step 1: Create a Docker Hub Account

1. Go to [hub.docker.com](https://hub.docker.com)
2. Sign up for a free account
3. Remember your username (e.g., `yourusername`)

### Step 2: Login from Terminal

```bash
docker login

# Enter your Docker Hub username and password
# Username: yourusername
# Password: ********
# Login Succeeded

# Or login with token (more secure, recommended for CI/CD)
echo $DOCKER_HUB_TOKEN | docker login -u yourusername --password-stdin
```

### Step 3: Tag Your Image for Docker Hub

Docker Hub requires images to be tagged as `username/repository:tag`.

```bash
# Your local image
docker images
# REPOSITORY      TAG    IMAGE ID
# my-express-app  1.0    abc123def

# Tag it for Docker Hub
docker tag my-express-app:1.0 yourusername/my-express-app:1.0
docker tag my-express-app:1.0 yourusername/my-express-app:latest

# Now you have:
# REPOSITORY                         TAG       IMAGE ID
# my-express-app                     1.0       abc123def
# yourusername/my-express-app        1.0       abc123def   (same image, new tag)
# yourusername/my-express-app        latest    abc123def   (same image, new tag)
```

### Step 4: Push to Docker Hub

```bash
docker push yourusername/my-express-app:1.0
docker push yourusername/my-express-app:latest

# Output:
# The push refers to repository [docker.io/yourusername/my-express-app]
# 5f70bf18a086: Pushed
# e90a847b6a60: Pushed
# 1.0: digest: sha256:abc123... size: 1234
```

### Step 5: Pull from Docker Hub (on Any Machine)

```bash
# Anyone (or any server) can now pull your image
docker pull yourusername/my-express-app:1.0

# And run it
docker run -d -p 3000:3000 yourusername/my-express-app:1.0
```

### Complete Push/Pull Workflow

```
YOUR MACHINE                          DOCKER HUB                         SERVER / TEAMMATE
                                                                         
1. Write code                         3. Image stored                    5. Pull image
2. Build & push image ──────────────► in registry ──────────────────────► 6. Run container
                                                                         
┌─────────────┐                     ┌─────────────┐                    ┌─────────────┐
│ Dockerfile  │  docker build       │  Docker Hub  │   docker pull     │   Server    │
│ app code    │────────────────────►│  yourusername│──────────────────►│ docker run  │
│             │  docker push        │  /my-app:1.0 │                   │ -d -p 3000  │
└─────────────┘                     └─────────────┘                    └─────────────┘
```

### Tagging Best Practices

```bash
# Semantic versioning
docker tag my-app:latest yourusername/my-app:1.0.0
docker tag my-app:latest yourusername/my-app:1.0
docker tag my-app:latest yourusername/my-app:1
docker tag my-app:latest yourusername/my-app:latest

# Git commit hash tagging (for CI/CD)
docker tag my-app:latest yourusername/my-app:$(git rev-parse --short HEAD)
# Result: yourusername/my-app:a1b2c3d

# Date-based tagging
docker tag my-app:latest yourusername/my-app:2025-02-08
```

| Tag Strategy | Example | When to Use |
|-------------|---------|-------------|
| Semantic version | `1.2.3` | Releases with clear versioning |
| Major.minor | `1.2` | Points to latest patch of that minor |
| Latest | `latest` | Always the most recent build |
| Git SHA | `a1b2c3d` | CI/CD pipelines, traceability |
| Date | `2025-02-08` | Nightly or scheduled builds |

Docker Hub free tier allows **1 private repository**. For more:

You can connect your GitHub repo to Docker Hub for **automated builds**:

1. Go to Docker Hub → Your Repository → Builds
2. Connect your GitHub account
3. Select the repository

### 2. `src/app.js`

```javascript
const express = require('express');
const app = express();

app.use(express.json());

// Routes
app.get('/', (req, res) => {
  res.json({
    message: 'Express server running in Docker!',
    environment: process.env.NODE_ENV || 'development',
    timestamp: new Date().toISOString()
  });
});

app.get('/health', (req, res) => {
  res.json({ status: 'OK', uptime: process.uptime() });
});

app.post('/api/data', (req, res) => {
  const data = req.body;
  res.json({ received: data, timestamp: new Date().toISOString() });
});

// Error handler
app.use((err, req, res, next) => {
  console.error(err.stack);
  res.status(500).json({ error: err.message });
});

const PORT = process.env.PORT || 3000;
app.listen(PORT, '0.0.0.0', () => {
  console.log(`Server running on port ${PORT}`);
  console.log(`Environment: ${process.env.NODE_ENV || 'development'}`);
});

module.exports = app;
```

```bash
docker compose exec db psql -U user -d mydb

# Stop everything
docker compose down

# Stop and delete all data
docker compose down -v
```

### 8. Push to Docker Hub

```bash
# Tag for Docker Hub
docker tag my-express-app:1.0 yourusername/express-app:1.0
docker tag my-express-app:1.0 yourusername/express-app:latest

# Push
docker push yourusername/express-app:1.0
docker push yourusername/express-app:latest

# Now anyone can run your app with:
# docker run -d -p 3000:3000 yourusername/express-app:1.0
```

## Multi-Stage Builds

Multi-stage builds let you use multiple `FROM` statements in a single Dockerfile. The final image only includes the output from the last stage, resulting in much smaller images.

### Why Multi-Stage?

```
Single-stage build:
  node:18-alpine + source code + ALL dependencies + build tools = ~500MB

Multi-stage build:
  Stage 1 (builder): Install everything, compile TypeScript, etc.
  Stage 2 (production): Copy only compiled output + production deps = ~150MB
```

### Node.js / Express Multi-Stage

```dockerfile
# ============ STAGE 1: Build ============
FROM node:18-alpine AS builder

WORKDIR /app

COPY package.json package-lock.json ./

# Install ALL dependencies (including devDependencies for build)
RUN npm ci

COPY . .

# Build step (TypeScript compilation, bundling, etc.)
RUN npm run build

# ============ STAGE 2: Production ============
FROM node:18-alpine

WORKDIR /app

# Copy only package files and install production deps
COPY package.json package-lock.json ./
RUN npm ci --only=production && npm cache clean --force

# Copy built output from builder stage
COPY --from=builder /app/dist ./dist

# Security: non-root user
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/health || exit 1

CMD ["node", "dist/server.js"]
```

### Python Multi-Stage

```dockerfile
# ============ STAGE 1: Build ============
FROM python:3.11-slim AS builder

WORKDIR /app

COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

COPY . .

# ============ STAGE 2: Production ============
FROM python:3.11-slim

WORKDIR /app

# Copy installed packages from builder
COPY --from=builder /root/.local /root/.local
COPY --from=builder /app .

ENV PATH=/root/.local/bin:$PATH

EXPOSE 8000

CMD ["python", "app.py"]
```

### Go Multi-Stage (Extremely Small Final Image)

```dockerfile
# ============ STAGE 1: Build ============
FROM golang:1.21-alpine AS builder

WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o server .

# ============ STAGE 2: Production ============
FROM scratch
# 'scratch' = completely empty image!

COPY --from=builder /app/server /server

EXPOSE 8080

ENTRYPOINT ["/server"]
# Final image size: ~10MB (just the Go binary!)
```

### Size Comparison

| Build Type | Node.js | Python | Go |
|-----------|---------|--------|----|
| Single-stage | ~500 MB | ~400 MB | ~300 MB |
| Multi-stage | ~150 MB | ~200 MB | ~10 MB |

## Debugging & Troubleshooting Containers

### Container Won't Start

```bash
# Check the logs — almost always shows the error
docker logs my-container

# Check container status and exit code
docker ps -a
# EXIT CODE meanings:
# 0   = normal exit
# 1   = application error
# 137 = killed (OOM or SIGKILL) — likely out of memory
# 143 = terminated gracefully (SIGTERM)
# 126 = command cannot execute
# 127 = command not found

# Inspect the container for detailed info
docker inspect my-container
```

### Can't Connect to the App

```bash
# 1. Is the container running?
docker ps

# 2. Are ports mapped correctly?
docker port my-container

# 3. Is the app actually listening?
docker exec my-container netstat -tlnp
# Or: docker exec my-container ss -tlnp

# 4. Test from inside the container
docker exec my-container wget -qO- http://localhost:3000

# 5. Check the app isn't binding to 127.0.0.1
# Your app should bind to 0.0.0.0 inside Docker, NOT 127.0.0.1
# Wrong: app.listen(3000, '127.0.0.1')
# Right: app.listen(3000, '0.0.0.0')  or just  app.listen(3000)
```

### Debugging Inside a Container

```bash
# Open a shell in a running container
docker exec -it my-container /bin/sh

# Inside the container you can:
ls -la                          # Check files
cat /app/package.json           # Read config
env                             # Check environment variables
node -v                         # Check runtime version
ping db                         # Test network connectivity
wget -qO- http://db:5432       # Test service connectivity
```

### Container Runs Out of Memory

```bash
# Check resource usage
docker stats my-container

# Set memory limits
docker run -m 512m my-app                    # Max 512 MB RAM
docker run -m 512m --memory-swap 1g my-app   # 512 MB RAM + 512 MB swap
```

### Image Build Fails

```bash
# Build with verbose output
DOCKER_BUILDKIT=0 docker build -t my-app .

# Build a specific stage (for multi-stage debugging)
docker build --target builder -t my-app-debug .

# Enter the failed build at the last successful layer
# (Use the layer hash from the build output)
docker run -it <last-successful-layer-hash> /bin/sh
```

### Common Mistakes

| Mistake | Symptom | Fix |
|---------|---------|-----|
| App binds to `127.0.0.1` | Can't connect from host | Bind to `0.0.0.0` |
| Forgot `-p` flag | Can't connect from host | Add `-p HOST:CONTAINER` |
| Wrong `CMD` in Dockerfile | Container exits immediately | Check command exists and is correct |
| Missing `.dockerignore` | Image is huge, builds slow | Add `.dockerignore` file |
| `node_modules` copied from host | Platform incompatible binaries | Use `.dockerignore` to exclude it |
| `COPY . .` before `npm install` | Cache busted on every code change | Copy `package.json` first, then install, then copy code |
| Using `latest` tag | Builds are not reproducible | Pin specific versions |

## Docker in CI/CD Pipelines

Docker fits naturally into CI/CD workflows. Here's a typical flow:

### The Workflow

```
Developer pushes code to GitHub
        │
        ▼
CI/CD Pipeline (GitHub Actions / GitLab CI / Jenkins)
        │
        ├── 1. Checkout code
        ├── 2. Run tests
        ├── 3. docker build -t myapp:$GIT_SHA .
        ├── 4. docker push myapp:$GIT_SHA
        │
        ▼
Deployment (Kubernetes / ECS / Docker Swarm)
        │
        ├── 5. docker pull myapp:$GIT_SHA
        └── 6. docker run myapp:$GIT_SHA
```

### GitHub Actions Example

```yaml
# .github/workflows/docker-build.yml
name: Build and Push Docker Image

on:
  push:
    branches: [main]

jobs:
  build-and-push:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ${{ secrets.DOCKER_USERNAME }}/my-app:latest
            ${{ secrets.DOCKER_USERNAME }}/my-app:${{ github.sha }}
```

**Setup required**:
1. Go to Docker Hub → Account Settings → Security → New Access Token
2. Go to GitHub Repo → Settings → Secrets → Add `DOCKER_USERNAME` and `DOCKER_TOKEN`
3. Push code to `main` — the pipeline will automatically build and push your image

### GitLab CI Example

```yaml
# .gitlab-ci.yml
stages:
  - build
  - deploy

build:
  stage: build
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
```

## Security Best Practices

### 1. Use Specific Image Versions

```dockerfile
# Good — pinned version
FROM node:18.19-alpine

# Bad — could change anytime
FROM node:latest
```

### 2. Run as Non-Root User

```dockerfile
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
```

### 3. Use `.dockerignore`

Prevent secrets and unnecessary files from being included in the image.

### 4. Don't Store Secrets in Images

```dockerfile
# NEVER do this:
ENV API_KEY=sk-12345
COPY .env /app/.env

# Instead, pass at runtime:
# docker run -e API_KEY=sk-12345 my-app
# docker run --env-file .env my-app
```

### 5. Scan Images for Vulnerabilities

```bash
# Docker Scout (built into Docker Desktop)
docker scout cves my-app:1.0

# Trivy (popular open-source scanner)
trivy image my-app:1.0

# Snyk
snyk container test my-app:1.0
```

### 6. Use Multi-Stage Builds

Smaller images = smaller attack surface.

### 7. Keep Images Updated

Regularly rebuild images to pick up security patches in base images.

### 8. Use Read-Only Filesystem When Possible

```bash
docker run --read-only --tmpfs /tmp my-app
```

### 9. Limit Resources

```bash
docker run --memory=512m --cpus=0.5 my-app
```

### 10. Don't Run Privileged Containers

```bash
# NEVER do this in production:
docker run --privileged my-app

# This gives the container full access to the host system
```

## Production Checklist

Before deploying a Dockerized app to production, verify:

### Image

- [ ] Using specific, pinned base image version (not `latest`)
- [ ] Multi-stage build to minimize image size
- [ ] `.dockerignore` excludes unnecessary files
- [ ] No secrets or credentials baked into the image
- [ ] Image scanned for vulnerabilities
- [ ] Non-root user configured

### Container

- [ ] Health checks configured
- [ ] Resource limits set (memory, CPU)
- [ ] Restart policy configured (`unless-stopped` or `always`)
- [ ] Logs are sent to a centralized logging system
- [ ] Graceful shutdown handling (app listens for SIGTERM)

### Data

- [ ] Persistent data uses named volumes
- [ ] Database backups configured
- [ ] Volume mount permissions are correct

### Networking

- [ ] Only necessary ports are exposed
- [ ] Internal services are NOT exposed to the host
- [ ] TLS/SSL termination configured (via reverse proxy like Nginx or Traefik)

### CI/CD

- [ ] Automated builds on push to main
- [ ] Automated image pushing to registry
- [ ] Automated deployments (or manual approval gate)
- [ ] Rollback strategy defined

## Common Docker Commands — Cheat Sheet

### Images

| Command | Description |
|---------|------------|
| `docker build -t name:tag .` | Build an image from Dockerfile |
| `docker images` | List all local images |
| `docker pull image:tag` | Download image from registry |
| `docker push image:tag` | Upload image to registry |
| `docker tag source:tag target:tag` | Create a new tag for an image |
| `docker rmi image:tag` | Remove an image |
| `docker image prune` | Remove dangling images |
| `docker image prune -a` | Remove all unused images |

### Containers

| Command | Description |
|---------|------------|
| `docker run -d --name c -p 3000:3000 img` | Run a container (detached, named, port mapped) |
| `docker ps` | List running containers |
| `docker ps -a` | List all containers (including stopped) |
| `docker stop name` | Stop a running container |
| `docker start name` | Start a stopped container |
| `docker restart name` | Restart a container |
| `docker rm name` | Remove a stopped container |
| `docker rm -f name` | Force remove a running container |
| `docker logs -f name` | Follow container logs |
| `docker exec -it name /bin/sh` | Open shell in running container |
| `docker inspect name` | Get detailed container info |
| `docker stats` | Live resource usage (CPU, memory, network) |
| `docker cp c:/path ./local` | Copy files from container to host |
| `docker cp ./local c:/path` | Copy files from host to container |
| `docker port name` | Show port mappings |

### Volumes

| Command | Description |
|---------|------------|
| `docker volume create name` | Create a named volume |
| `docker volume ls` | List all volumes |
| `docker volume inspect name` | Show volume details |

### Networks

| Command | Description |
|---------|------------|
| `docker network create name` | Create a network |
| `docker network ls` | List all networks |

| `docker network connect net container` | Connect container to network |

| `docker network rm name` | Remove a network |

### Docker Compose

| Command | Description |
|---------|------------|
| `docker compose up -d` | Start all services (detached) |

### Cleanup

| Command | Description |
|---------|------------|
| `docker system prune` | Remove stopped containers, dangling images, unused networks |

| `docker system df` | Show Docker disk usage |

### Quick Reference: The Daily Workflow

```bash

# Testing a new build
docker compose up -d --build     # Rebuild and restart

# End of day: Stop everything
docker compose down

# Weekly: Clean up

# Release day: Push to Docker Hub
docker build -t yourusername/app:1.0 .
docker push yourusername/app:1.0
```
