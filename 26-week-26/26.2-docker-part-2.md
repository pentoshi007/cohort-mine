## 1. Layers in Docker

### What Are Layers?

Think of a Docker image like a **layer cake**. Each instruction in your Dockerfile adds a new layer on top of the previous one. These layers stack up to form the complete image.

```
┌─────────────────────────────────────────────────┐
│   Writable Layer (Container)                    │  ← Changes during runtime (temporary)
├─────────────────────────────────────────────────┤
│   Layer 5: CMD ["node", "index.js"]             │  ← What command to run
├─────────────────────────────────────────────────┤
│   Layer 4: COPY . .                             │  ← Your application code
├─────────────────────────────────────────────────┤
│   Layer 3: RUN npm install                      │  ← Dependencies installed
├─────────────────────────────────────────────────┤
│   Layer 2: COPY package.json .                  │  ← Package file copied
├─────────────────────────────────────────────────┤
│   Layer 1: FROM node:22-alpine                  │  ← Base OS + Node.js runtime
└─────────────────────────────────────────────────┘
```

### Key Rules About Layers

1. **Every instruction in a Dockerfile creates a layer** — `FROM`, `COPY`, `RUN`, `CMD`, etc.
2. **Layers are read-only** — Once created, they never change.
3. **Layers are cached** — Docker remembers each layer and reuses it if nothing changed.
4. **Containers add a thin writable layer on top** — Any file changes at runtime happen here. When the container is deleted, this writable layer is gone.

### Analogy: Think of It Like Git Commits

| Git | Docker Layers |
| --- | --- |
| Each commit saves changes | Each Dockerfile instruction saves a layer |
| You can see history with `git log` | You can see layers with `docker history` |
| Commits are immutable | Layers are immutable (read-only) |
| New commits build on previous ones | New layers build on previous ones |

### Which Dockerfile Instructions Create Layers?

| Instruction | Creates a Layer? | What It Does |
| --- | --- | --- |
| `FROM` | Yes (base layer) | Sets the base image |
| `RUN` | Yes | Executes a command (install packages, build code) |
| `COPY` | Yes | Copies files from host to image |
| `ADD` | Yes | Like COPY, but also handles URLs and tar extraction |
| `WORKDIR` | Yes (metadata) | Sets working directory |
| `ENV` | Yes (metadata) | Sets environment variables |
| `EXPOSE` | Yes (metadata) | Documents which port the container listens on |
| `CMD` | Yes (metadata) | Default command to run |
| `ENTRYPOINT` | Yes (metadata) | Configures container as executable |

> **Note**: Metadata layers (`WORKDIR`, `ENV`, `EXPOSE`, `CMD`) are 0 bytes — they don't add to image size but are still considered layers.

## 2. Layer Caching — Why Order Matters

### How Caching Works

Docker caching is the **single most important concept** for fast builds. Here's the rule:

> **If a layer hasn't changed, Docker uses the cached version. If a layer changes, Docker rebuilds that layer AND every layer after it.**

Think of it like a domino chain — once one domino falls (a layer changes), every domino after it falls too.

```
Layer 1: FROM node:22-alpine          → unchanged → CACHED ⚡
Layer 2: WORKDIR /app                 → unchanged → CACHED ⚡
Layer 3: COPY package.json .          → unchanged → CACHED ⚡
Layer 4: RUN npm install              → unchanged → CACHED ⚡
Layer 5: COPY . .                     → CHANGED!  → REBUILD 🔨
Layer 6: CMD ["node", "index.js"]     → must rebuild (after changed layer) 🔨
```

### Example: First Build vs. Second Build

#### First Build (Everything is New)

```
Build 1 (first time):
├── Layer 1: FROM node:22-alpine          [BUILD] ✅
├── Layer 2: WORKDIR /app                 [BUILD] ✅
├── Layer 3: COPY package.json .          [BUILD] ✅
├── Layer 4: COPY package-lock.json .     [BUILD] ✅
├── Layer 5: RUN npm install              [BUILD] ✅ (takes 30 seconds)
├── Layer 6: COPY . .                     [BUILD] ✅
├── Layer 7: EXPOSE 3000                  [BUILD] ✅
└── Layer 8: CMD ["node", "index.js"]     [BUILD] ✅
Total time: ~45 seconds
```

#### Second Build (Only Application Code Changed)

```
Build 2 (only your .js/.ts files changed):
├── Layer 1: FROM node:22-alpine          [CACHED] ⚡ (instant)
├── Layer 2: WORKDIR /app                 [CACHED] ⚡ (instant)
├── Layer 3: COPY package.json .          [CACHED] ⚡ (instant)
├── Layer 4: COPY package-lock.json .     [CACHED] ⚡ (instant)
├── Layer 5: RUN npm install              [CACHED] ⚡ (instant — saved 30 seconds!)
├── Layer 6: COPY . .                     [BUILD] ✅ (code changed)
├── Layer 7: EXPOSE 3000                  [BUILD] ✅
└── Layer 8: CMD ["node", "index.js"]     [BUILD] ✅
Total time: ~2 seconds ⚡
```

### The Golden Rule: Order by Frequency of Change

Put things that change **rarely** at the top, things that change **often** at the bottom.

```
RARELY CHANGES    ┌──────────────────────────────────┐
                  │  FROM node:22-alpine             │  ← Almost never changes
                  │  WORKDIR /app                    │  ← Never changes
                  │  COPY package*.json ./           │  ← Changes when you add a dependency
                  │  RUN npm install                 │  ← Changes when dependencies change
OFTEN CHANGES     │  COPY . .                        │  ← Changes every time you edit code
                  │  CMD ["node", "index.js"]        │  ← Rarely changes
                  └──────────────────────────────────┘
```

### BAD vs GOOD Dockerfile

#### BAD — Slow Rebuilds Every Time

```dockerfile
FROM node:22-alpine
WORKDIR /app

COPY . .                    # ❌ Copies EVERYTHING first (including source code)
RUN npm install             # ❌ Reinstalls all deps even if only code changed!

CMD ["node", "index.js"]
```

**Why it's bad**: You edit `index.js` → `COPY . .` layer changes → `RUN npm install` has to run again → 30+ seconds wasted every time.

#### GOOD — Fast Rebuilds

```dockerfile
FROM node:22-alpine
WORKDIR /app

COPY package.json .                    # ✅ Copy dependency file first
COPY package-lock.json .               # ✅ Copy lock file
RUN npm install                        # ✅ Cached unless package.json changed

COPY . .                               # ✅ Copy code last (changes often)

CMD ["node", "index.js"]
```

**Why it's good**: You edit `index.js` → only `COPY . .` layer changes → `npm install` is cached → rebuild takes ~2 seconds.

## 4. Image Size Optimization

Smaller images = faster downloads, faster deployments, smaller attack surface. Here's how to optimize.

### Strategy 1: Use Alpine-Based Images

Alpine Linux is a minimal Linux distribution (~5MB base). Most official images offer Alpine variants.

| Image | Size |
| --- | --- |
| `node:22` | ~900MB |
| `node:22-slim` | ~200MB |
| `node:22-alpine` | ~120MB |

```dockerfile
# ❌ Don't use this (huge)
FROM node:22

# ✅ Use this (small)
FROM node:22-alpine
```

### Strategy 2: Use `.dockerignore`

Just like `.gitignore`, a `.dockerignore` file tells Docker what NOT to copy into the image.

Create a `.dockerignore` file in your project root:

```
node_modules
npm-debug.log
.git
.gitignore
.env
Dockerfile
docker-compose.yml
.dockerignore
README.md
.vscode
coverage
.nyc_output
dist
```

**Why this matters**: Without `.dockerignore`, `COPY . .` copies everything — including your local `node_modules` (which could be 500MB+ and built for your OS, not the container's OS).

### Strategy 3: Combine RUN Commands

Each `RUN` creates a layer. Combine related commands to reduce layers and clean up in the same layer.

```dockerfile
# ❌ BAD — 3 separate layers, cache from apt-get persists
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# ✅ GOOD — 1 layer, cleanup happens in same layer
RUN apt-get update && \
    apt-get install -y curl && \
    rm -rf /var/lib/apt/lists/*
```

**Why combining matters**: If you `RUN apt-get install` in one layer and `RUN rm -rf /var/lib/apt/lists/*` in another layer, the files are still in the first layer (layers are immutable). The delete only marks them as deleted in the new layer but the image size doesn't decrease.

### Strategy 4: Use `npm ci` Instead of `npm install`

| `npm install` | `npm ci` |
| --- | --- |
| Reads `package.json` | Reads `package-lock.json` |
| May update lock file | Never updates lock file |
| Non-deterministic | Deterministic (exact versions) |
| Slower | Faster (skips dependency resolution) |

```dockerfile
# ❌ Non-deterministic
RUN npm install

# ✅ Deterministic & faster
RUN npm ci
```

For production, install only production dependencies:

```dockerfile
RUN npm ci --only=production && npm cache clean --force
```

### Strategy 5: Add a Non-Root User (Security)

By default, containers run as root. This is a security risk. Always create and switch to a non-root user.

```dockerfile
# Create a group and user
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

# Switch to non-root user
USER appuser
```

### Strategy 6: Add Health Checks

Health checks let Docker (and orchestrators like Kubernetes) know if your app is actually running properly.

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/health || exit 1
```

| Flag | Meaning |
| --- | --- |
| `--interval=30s` | Check every 30 seconds |
| `--timeout=5s` | Fail if check takes more than 5 seconds |
| `--start-period=10s` | Wait 10s before first check (app startup time) |
| `--retries=3` | Mark unhealthy after 3 consecutive failures |

### Complete Optimized Dockerfile Example

```dockerfile
FROM node:22-alpine

WORKDIR /app

# Copy dependency files first (cached layer)
COPY package*.json ./

# Install production deps only + clean cache
RUN npm ci --only=production && \
    npm cache clean --force

# Copy source code (frequently changing layer)
COPY . .

# Security: non-root user
RUN addgroup -S appgroup && \
    adduser -S appuser -G appgroup
USER appuser

# Document port
EXPOSE 3000

# Health check
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/health || exit 1

# Start application
CMD ["node", "index.js"]
```

### Optimization Tips Summary Table

| Tip | Why | Example |
| --- | --- | --- |
| Order by frequency of change | Frequently changing layers invalidate cache | Put `COPY . .` last |
| Combine RUN commands | Each RUN = one layer | `RUN npm install && npm cache clean` |
| Use `.dockerignore` | Exclude unnecessary files | `node_modules`, `.git`, etc. |
| Use multi-stage builds | Remove build artifacts | Builder stage → production stage |
| Pin base image version | Ensure reproducible builds | `node:22-alpine`, not `node:latest` |
| Use alpine images | Much smaller base | `node:22-alpine` (~120MB) vs `node:22` (~900MB) |
| Clean package cache | Reduce layer size | `npm cache clean --force` |
| Use non-root user | Security best practice | `USER appuser` |

## 5. Multi-Stage Builds

### The Problem

When you build a TypeScript project, you need:
- TypeScript compiler (`tsc`)
- All dev dependencies (`@types/*`, testing libraries, linters)
- Source `.ts` files

But in production, you **only** need:
- The compiled `.js` files
- Production dependencies

Including build tools in your production image is wasteful and insecure.

### The Solution: Multi-Stage Builds

A multi-stage build uses multiple `FROM` instructions. Each `FROM` starts a new "stage". You can copy artifacts from one stage to another, leaving behind everything you don't need.

### Anatomy of a Multi-Stage Build

```dockerfile
# ============================================
# STAGE 1: Builder (temporary — discarded)
# ============================================
FROM node:22-alpine AS builder

WORKDIR /app

COPY package*.json ./
RUN npm ci                         # Install ALL dependencies (dev + prod)

COPY . .
RUN npm run build                  # Compile TypeScript → JavaScript (outputs to /app/dist)

# ============================================
# STAGE 2: Production (final image)
# ============================================
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./
RUN npm ci --only=production       # Install ONLY production dependencies

# Copy compiled code from the builder stage
COPY --from=builder /app/dist ./dist

# Security
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

EXPOSE 3000

CMD ["node", "dist/index.js"]
```

### How It Works — Visual Breakdown

```
STAGE 1: "builder" (TEMPORARY)
┌──────────────────────────────────────────────┐
│  node:22-alpine (base)                       │
│  + ALL npm packages (dev + prod)             │
│  + TypeScript source files (.ts)             │
│  + Compiled JavaScript files (.js) in /dist  │
│  + Build tools, linters, test frameworks     │
│                                              │
│  Size: ~400MB                                │
│                                              │
│  ⬇️ Only /app/dist is copied to Stage 2      │
└──────────────────────────────────────────────┘
                    │
                    ▼  COPY --from=builder /app/dist ./dist
                    │
STAGE 2: "production" (FINAL IMAGE)
┌──────────────────────────────────────────────┐
│  node:22-alpine (fresh base)                 │
│  + Production npm packages only              │
│  + Compiled JavaScript files (.js)           │
│                                              │
│  Size: ~100MB  (75% smaller!)                │
│                                              │
│  ❌ No TypeScript source files               │
│  ❌ No dev dependencies                      │
│  ❌ No build tools                           │
│  ❌ No test frameworks                       │
└──────────────────────────────────────────────┘
```

### Size Comparison

| Approach | Image Size | Contents |
| --- | --- | --- |
| Single-stage | ~400MB | Everything (dev deps, source, build tools) |
| Multi-stage | ~100MB | Only production deps + compiled code |

### Real-World Multi-Stage Example (TypeScript + Express)

```dockerfile
# ---- Stage 1: Build ----
FROM node:22-alpine AS builder

WORKDIR /app

COPY package*.json ./
COPY tsconfig.json ./
RUN npm ci

COPY src/ ./src/
RUN npm run build

# ---- Stage 2: Production ----
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./
RUN npm ci --only=production && npm cache clean --force

COPY --from=builder /app/dist ./dist

RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=5s \
  CMD wget --no-verbose --tries=1 --spider http://localhost:3000/health || exit 1

CMD ["node", "dist/index.js"]
```

## 6. Docker Volumes — Persisting Data

### The Problem: Containers Are Ephemeral

By default, all data inside a container lives in the **writable layer**. When the container is removed, all that data is gone.

```
Container running MongoDB:
┌──────────────────────────────────┐
│  Writable Layer                  │  ← MongoDB writes data here
│  /data/db/                       │
│    ├── collection-0.wt           │
│    ├── collection-1.wt           │
│    └── ...                       │
├──────────────────────────────────┤
│  Read-Only Image Layers          │
│  (MongoDB base image)            │
└──────────────────────────────────┘

When you run `docker rm mongo-container`:
  ❌ All data in /data/db/ is PERMANENTLY LOST
  ❌ All your database records are GONE
```

### The Solution: Volumes

A **volume** is a directory on your **host machine** that is mounted into the container. Data written to this directory persists even after the container is removed.

```
Host Machine                          Container
┌────────────────┐                   ┌──────────────────────┐
│                │                   │                      │
│  /docker-data/ │ ◄═══ mounted ═══►│  /data/db/           │
│  mongo-data/   │                   │  (MongoDB data dir)  │
│                │                   │                      │
└────────────────┘                   └──────────────────────┘

When you run `docker rm mongo-container`:
  ✅ Container is removed
  ✅ Data in /docker-data/mongo-data/ STILL EXISTS on host
  ✅ Start a new container, mount the same volume → data is back!
```

### Types of Volumes

Docker provides three ways to persist data:

#### 1. Named Volumes (Recommended)

Docker manages the storage location. You just give it a name.

```bash
# Create a named volume
docker volume create mongo-data

# Run container with volume mounted
docker run -d \
  --name mongodb \
  -v mongo-data:/data/db \
  mongo:7

# Even after removing the container, data persists
docker rm -f mongodb

# Start a new container with the same volume — data is still there!
docker run -d \
  --name mongodb-new \
  -v mongo-data:/data/db \
  mongo:7
```

#### 2. Bind Mounts (Map Host Directory)

You specify an exact path on your host machine.

```bash
# Map a specific host directory to container
docker run -d \
  --name mongodb \
  -v /Users/yourname/mongo-data:/data/db \
  mongo:7

# Or using $(pwd) for current directory
docker run -d \
  --name mongodb \
  -v $(pwd)/mongo-data:/data/db \
  mongo:7
```

#### 3. tmpfs Mounts (Temporary — RAM Only)

Data stored in memory, not on disk. Gone when container stops.

```bash
docker run -d \
  --name temp-app \
  --tmpfs /app/temp \
  my-app
```

### Named Volumes vs Bind Mounts

| Feature | Named Volumes | Bind Mounts |
| --- | --- | --- |
| Managed by | Docker | You |
| Storage location | Docker-managed path | You specify exact path |
| Portability | Works on any OS | Path may differ across OS |
| Backup | `docker volume` commands | Standard file tools |
| Best for | Database data, persistent storage | Development (hot reload) |
| Syntax | `-v my-vol:/data` | `-v /host/path:/container/path` |

### Volume Management Commands

```bash
# Create a volume
docker volume create my-volume

# List all volumes
docker volume ls

# Inspect a volume (see where it's stored)
docker volume inspect my-volume
# Output:
# [
#   {
#     "Name": "my-volume",
#     "Driver": "local",
#     "Mountpoint": "/var/lib/docker/volumes/my-volume/_data",
#     ...
#   }
# ]

# Remove a volume
docker volume rm my-volume

# Remove ALL unused volumes (be careful!)
docker volume prune
```

### Practical Example: Persisting MongoDB Data

```bash
# Step 1: Create a named volume
docker volume create mongo-data

# Step 2: Run MongoDB with the volume
docker run -d \
  --name my-mongo \
  -p 27017:27017 \
  -v mongo-data:/data/db \
  mongo:7

# Step 3: Connect and add data
docker exec -it my-mongo mongosh
# > use mydb
# > db.users.insertOne({ name: "Alice", age: 25 })
# > db.users.find()   // shows Alice
# > exit

# Step 4: Remove the container
docker rm -f my-mongo

# Step 5: Start a NEW container with the SAME volume
docker run -d \
  --name my-mongo-2 \
  -p 27017:27017 \
  -v mongo-data:/data/db \
  mongo:7

# Step 6: Verify data persisted!
docker exec -it my-mongo-2 mongosh
# > use mydb
# > db.users.find()   // Alice is still there! ✅
```

## 7. Docker Networks — Container Communication

### The Problem: Containers Are Isolated

By default, each container runs in its own isolated network. Your Express app container can't reach your MongoDB container, even if both are running on the same machine.

```
Without networking:

┌─────────────────┐          ┌─────────────────┐
│  Express App    │    ❌    │   MongoDB       │
│  Container      │ ──────── │   Container     │
│                 │ Can't    │                 │
│  localhost:3000 │ connect! │  localhost:27017│
└─────────────────┘          └─────────────────┘
```

### The Solution: Docker Networks

Create a **Docker network** and attach both containers to it. Containers on the same network can communicate using their **container names** as hostnames.

```
With Docker network "my-network":

┌──────────────────────────────────────────────────┐
│  Network: my-network                             │
│                                                  │
│  ┌─────────────────┐    ┌─────────────────┐     │
│  │  Express App    │    │   MongoDB       │     │
│  │  Name: app      │───►│   Name: mongo   │     │
│  │                 │    │                 │     │
│  │  Connects to:   │    │  Port: 27017   │     │
│  │  mongo:27017 ✅ │    │                 │     │
│  └─────────────────┘    └─────────────────┘     │
│                                                  │
└──────────────────────────────────────────────────┘
```

### Network Types

| Network Type | Description | Use Case |
| --- | --- | --- |
| `bridge` (default) | Isolated network for containers on same host | Most common for local dev |
| `host` | Container shares host's network | Performance (no network isolation) |
| `none` | No networking | Security-sensitive containers |
| `overlay` | Multi-host networking | Docker Swarm / multi-machine setups |

### Network Commands

```bash
# Create a custom network
docker network create my-network

# List all networks
docker network ls

# Inspect a network
docker network inspect my-network

# Run a container on a specific network
docker run -d --name my-app --network my-network my-image

# Connect an existing container to a network
docker network connect my-network existing-container

# Disconnect a container from a network
docker network disconnect my-network container-name

# Remove a network
docker network rm my-network

# Remove all unused networks
docker network prune
```

### How DNS Resolution Works in Docker Networks

When containers are on the same custom network, Docker provides built-in DNS. You can use the **container name** as the hostname.

```bash
# Start MongoDB on custom network
docker run -d \
  --name mongo \
  --network my-network \
  mongo:7

# Start Express app on the same network
docker run -d \
  --name app \
  --network my-network \
  -p 3000:3000 \
  my-express-app

# Inside the "app" container, you can connect to MongoDB using:
#   mongodb://mongo:27017/mydb
#
# "mongo" resolves to the MongoDB container's IP address
# because they're on the same Docker network!
```

### Important: Default Bridge vs Custom Bridge

```bash
# ❌ Default bridge network — NO DNS resolution between containers
docker run -d --name mongo mongo:7
docker run -d --name app my-app
# "app" container CANNOT reach "mongo" by name

# ✅ Custom bridge network — DNS resolution works!
docker network create my-network
docker run -d --name mongo --network my-network mongo:7
docker run -d --name app --network my-network my-app
# "app" container CAN reach "mongo" by name ✅
```

> **Key Takeaway**: Always create and use a custom network. Never rely on the default bridge network for inter-container communication.

## 8. Real-World Project: Express + MongoDB in Containers

Let's build a complete TypeScript Express app with MongoDB, both running in containers, connected via a Docker network with persistent data.

### Project Structure

```
my-docker-app/
├── src/
│   └── index.ts             # Express app with MongoDB connection
├── package.json
├── tsconfig.json
├── Dockerfile               # Multi-stage build
├── .dockerignore
└── docker-compose.yml       # Orchestrates both containers
```

### Step 1: Initialize the Project

```bash
mkdir my-docker-app && cd my-docker-app
npm init -y
npm install express mongoose
npm install -D typescript @types/express @types/node ts-node
npx tsc --init
```

### Step 2: `tsconfig.json`

```json
{
  "compilerOptions": {
```

### Step 4: `src/index.ts` — The Express App

```typescript
import express, { Request, Response } from "express";
import mongoose from "mongoose";

const app = express();
app.use(express.json());

// -------------------------------------------
// MongoDB Connection
// -------------------------------------------
// MONGO_URL comes from environment variable
// In Docker, "mongo" is the container name (DNS resolves it)
// Fallback to localhost for local development
const MONGO_URL = process.env.MONGO_URL || "mongodb://localhost:27017/mydb";
const PORT = process.env.PORT || 3000;

mongoose
  .connect(MONGO_URL)
  .then(() => console.log("✅ Connected to MongoDB"))
  .catch((err) => console.error("❌ MongoDB connection error:", err));

// -------------------------------------------
// Mongoose Schema & Model
// -------------------------------------------
const userSchema = new mongoose.Schema({
  name: { type: String, required: true },
  email: { type: String, required: true, unique: true },
  createdAt: { type: Date, default: Date.now },
});

const User = mongoose.model("User", userSchema);

// -------------------------------------------
// Routes
// -------------------------------------------

// Health Check Endpoint (used by Docker HEALTHCHECK)
app.get("/health", async (_req: Request, res: Response) => {
  try {
    // Check if MongoDB is connected
    const dbState = mongoose.connection.readyState;
    // 0 = disconnected, 1 = connected, 2 = connecting, 3 = disconnecting
    if (dbState === 1) {
      res.status(200).json({ status: "healthy", db: "connected" });
    } else {
      res.status(503).json({ status: "unhealthy", db: "disconnected" });
    }
  } catch (error) {
    res.status(503).json({ status: "unhealthy", error: String(error) });
  }
});

// GET all users
app.get("/users", async (_req: Request, res: Response) => {
  try {
    const users = await User.find();
    res.json(users);
  } catch (error) {
    res.status(500).json({ error: "Failed to fetch users" });
  }
});

// POST create a user
app.post("/users", async (req: Request, res: Response) => {
  try {
    const { name, email } = req.body;
    const user = new User({ name, email });
    await user.save();
    res.status(201).json(user);
  } catch (error) {
    res.status(500).json({ error: "Failed to create user" });
  }
});

// DELETE a user
app.delete("/users/:id", async (req: Request, res: Response) => {
  try {
    await User.findByIdAndDelete(req.params.id);
    res.json({ message: "User deleted" });
  } catch (error) {
    res.status(500).json({ error: "Failed to delete user" });
  }
});

// -------------------------------------------
// Start Server
// -------------------------------------------
app.listen(PORT, () => {
  console.log(`🚀 Server running on port ${PORT}`);
  console.log(`📦 Connecting to MongoDB at: ${MONGO_URL}`);
});
```

## 9. Docker Compose — Managing Multi-Container Apps

Running multiple `docker run` commands with all those flags is tedious and error-prone. **Docker Compose** lets you define everything in a single YAML file.

### What Is Docker Compose?

Docker Compose is a tool for defining and running multi-container Docker applications. With a single file (`docker-compose.yml`) and a single command (`docker compose up`), you can spin up your entire stack.

### `docker-compose.yml`

```yaml
version: "3.8"

services:
  # -------------------------------------------
  # MongoDB Service
  # -------------------------------------------
  mongo:
    image: mongo:7                          # Official MongoDB image
    container_name: mongo                   # Fixed container name
    restart: unless-stopped                 # Auto-restart on crash
    ports:
      - "27017:27017"                       # Expose to host (optional for dev)
    volumes:
      - mongo-data:/data/db                 # Persist data to named volume
    networks:
      - app-network                         # Connect to custom network
    healthcheck:
      test: ["CMD", "mongosh", "--eval", "db.adminCommand('ping')"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 10s

  # -------------------------------------------
  # Express App Service
  # -------------------------------------------
  app:
    build:
      context: .                            # Build from current directory
      dockerfile: Dockerfile                # Use our Dockerfile
    container_name: app
    restart: unless-stopped
    ports:
      - "3000:3000"                         # Expose app on port 3000
    environment:
      - MONGO_URL=mongodb://mongo:27017/mydb  # "mongo" = service name (DNS)
      - PORT=3000
    depends_on:
      mongo:
        condition: service_healthy           # Wait for MongoDB to be healthy
    networks:
      - app-network

# -------------------------------------------
# Named Volumes
# -------------------------------------------
volumes:
  mongo-data:                               # Docker manages this volume

# -------------------------------------------
# Custom Network
# -------------------------------------------
networks:
  app-network:
    driver: bridge
```

### Docker Compose Commands

```bash
# Start everything (build + run)
docker compose up --build

# Start in detached mode (background)
docker compose up -d --build

# View logs
docker compose logs -f          # All services
docker compose logs -f app      # Just the app

# Stop everything
docker compose down

# Stop and remove volumes (DELETES DATA!)
docker compose down -v

# Restart a specific service
docker compose restart app

# Check status
docker compose ps

# Execute a command in a running service
docker compose exec app sh                    # Shell into app
docker compose exec mongo mongosh             # Open MongoDB shell
```

### Docker Compose — Key Concepts Explained

#### `depends_on` with Health Checks

```yaml
depends_on:
  mongo:
    condition: service_healthy
```

This means: "Don't start the `app` service until `mongo` is healthy." Without this, your app might try to connect to MongoDB before it's ready.

#### `restart: unless-stopped`

```yaml
restart: unless-stopped
```

| Policy | Behavior |
| --- | --- |
| `no` | Never restart (default) |
| `always` | Always restart |
| `on-failure` | Restart only on non-zero exit code |
| `unless-stopped` | Restart unless manually stopped |

#### Environment Variables

```yaml
environment:
  - MONGO_URL=mongodb://mongo:27017/mydb
  - PORT=3000
```

These are injected into the container as environment variables, accessible via `process.env.MONGO_URL` in Node.js.

#### Service Name = Hostname

In Docker Compose, the **service name** (e.g., `mongo`) automatically becomes the hostname on the network. That's why `mongodb://mongo:27017` works — `mongo` resolves to the MongoDB container's IP.

## 11. Interview Questions & Answers

### Beginner Level

---

**Q1: What are Docker layers?**

**A:** Docker layers are the building blocks of Docker images. Each instruction in a Dockerfile (`FROM`, `RUN`, `COPY`, etc.) creates a new read-only layer. These layers are stacked on top of each other to form the complete image. When a container runs, a thin writable layer is added on top where runtime changes happen.

---

**Q2: Why is layer ordering important in a Dockerfile?**

**A:** Because of Docker's caching mechanism. Docker caches each layer. If a layer changes, Docker rebuilds that layer *and all layers after it*. So if you put frequently changing files (like source code) at the top, it invalidates the cache for all subsequent layers (like `npm install`), causing slow rebuilds. The best practice is to put things that change rarely at the top and things that change often at the bottom.

---

**Q3: What is the difference between `COPY` and `ADD` in a Dockerfile?**

**A:** Both copy files from host to container. `COPY` is straightforward — it just copies files. `ADD` does everything `COPY` does plus: (1) it can extract tar archives automatically, and (2) it can download files from URLs. Best practice is to use `COPY` unless you specifically need `ADD`'s extra features, as `COPY` is more transparent and predictable.

---

**Q4: What is a `.dockerignore` file?**

**A:** It's like `.gitignore` but for Docker builds. It tells Docker which files and directories to exclude when copying files into the image (during `COPY` or `ADD`). Common entries include `node_modules`, `.git`, `.env`, and `dist`. This reduces image size, speeds up builds, and prevents accidentally including sensitive files.

---

**Q5: What happens to data when a Docker container is removed?**

**A:** All data stored inside the container's writable layer is permanently lost. To persist data beyond a container's lifecycle, you need to use Docker volumes or bind mounts that store data on the host machine.

---

**Q6: What is the difference between `docker stop` and `docker rm`?**

**A:** `docker stop` sends a SIGTERM signal to gracefully stop the container's process, but the container still exists (in "stopped" state) and can be restarted. `docker rm` removes the container entirely, deleting its writable layer. You need to stop a container before removing it, or use `docker rm -f` to force remove.

---

### Intermediate Level

---

**Q7: What are multi-stage builds and why use them?**

**A:** Multi-stage builds use multiple `FROM` instructions in a single Dockerfile. Each `FROM` starts a new "stage." You can copy specific artifacts from one stage to another using `COPY --from=<stage>`. This is useful because you can have a "builder" stage with all build tools (TypeScript compiler, dev dependencies) and a "production" stage with only the compiled output and production dependencies. The final image is much smaller and more secure since it doesn't contain build tools.

---

**Q8: Explain the difference between Named Volumes and Bind Mounts.**

**A:**
- **Named Volumes**: Managed by Docker, stored in Docker's internal directory. Created with `docker volume create`. More portable across OS. Best for production data (databases).
- **Bind Mounts**: Map a specific host directory to a container directory. You control the exact path. Best for development (e.g., mounting source code for hot reload). Less portable since paths differ across operating systems.

---

**Q9: How do containers communicate with each other?**

**A:** Containers communicate through Docker networks. When containers are on the same custom bridge network, they can reach each other using their container names as hostnames (Docker provides built-in DNS resolution). For example, if a MongoDB container is named `mongo` and an app container is named `app`, and both are on the same network, the app can connect to `mongodb://mongo:27017`. Important: this DNS resolution only works on custom networks, not the default bridge network.

---

**Q10: What is the difference between `CMD` and `ENTRYPOINT`?**

**A:**
- **`CMD`**: Sets the default command. Can be overridden when running the container (`docker run my-image <new-command>`).
- **`ENTRYPOINT`**: Sets the main command that always runs. Arguments from `CMD` or `docker run` are appended to it.

```dockerfile
# CMD example: can be overridden
CMD ["node", "index.js"]
# docker run my-app             → runs: node index.js
# docker run my-app sh          → runs: sh (CMD overridden)

# ENTRYPOINT example: always runs
ENTRYPOINT ["node"]
CMD ["index.js"]
# docker run my-app             → runs: node index.js
# docker run my-app server.js   → runs: node server.js (appended to ENTRYPOINT)
```

---

**Q11: What is `npm ci` and why is it preferred in Dockerfiles?**

**A:** `npm ci` (clean install) is designed for CI/CD and Docker environments. Unlike `npm install`, it:
1. Reads `package-lock.json` (not `package.json`) for exact versions
2. Deletes `node_modules` before installing (clean slate)
3. Never writes to `package-lock.json`
4. Fails if `package-lock.json` is out of sync with `package.json`
5. Is faster because it skips dependency resolution

This makes builds deterministic — you get the exact same dependencies every time.

---

**Q12: Why should you use a non-root user in Docker containers?**

**A:** By default, processes in containers run as root. If an attacker exploits a vulnerability in your app, they get root access inside the container. While container isolation limits damage, running as a non-root user adds defense-in-depth. In Kubernetes environments, many clusters enforce non-root containers via PodSecurityPolicies.

---

### Advanced Level

---

**Q13: Explain how Docker layer caching works with `COPY` instructions.**

**A:** Docker uses checksums to determine if a `COPY` layer has changed. For `COPY`, Docker computes a checksum of all the files being copied. If the checksum matches the previous build, the layer is cached. This is why we separate `COPY package*.json ./` from `COPY . .` — the package files rarely change, so their layer (and the subsequent `npm install` layer) stays cached. When only source code changes, only the `COPY . .` layer and everything after it rebuilds.

---

**Q14: What happens when a layer in the middle of the Dockerfile changes?**

**A:** Docker rebuilds that layer and every layer after it. Layers before the changed layer remain cached. This cascade effect is why Dockerfile instruction ordering is crucial. For example, if you have 8 layers and layer 3 changes, layers 3-8 are rebuilt while layers 1-2 are cached.

---

**Q15: How does Docker Compose `depends_on` with health checks work? Why is it important?**

**A:** `depends_on` controls startup order. With `condition: service_healthy`, Docker Compose waits until the dependency's health check passes before starting the dependent service. Without this, your app might start before the database is ready, causing connection errors. The health check is defined in the dependency's service configuration and Docker periodically runs it to determine service health.

```yaml
depends_on:
  mongo:
    condition: service_healthy    # Wait for mongo's healthcheck to pass
```

---

**Q16: What is the difference between the default bridge network and a custom bridge network?**

**A:**
1. **DNS Resolution**: Custom bridge networks provide automatic DNS resolution (containers can reach each other by name). The default bridge does not — you must use `--link` (deprecated) or IP addresses.
2. **Isolation**: Custom networks provide better isolation. Containers on different custom networks can't communicate.
3. **Configuration**: Custom networks can be configured with specific subnets, gateways, and other options.
4. **Recommendation**: Always use custom bridge networks for multi-container applications.

---

**Q17: How would you reduce Docker image size from 1GB to under 100MB?**

**A:** Multiple strategies combined:
1. **Switch to Alpine base image** (saves 600-800MB vs Ubuntu/Debian)
2. **Multi-stage build** (keep only compiled code and production deps in final image)
3. **`npm ci --only=production`** (exclude dev dependencies)
4. **Clean package cache** (`npm cache clean --force`)
5. **Use `.dockerignore`** (exclude node_modules, .git, tests)
6. **Combine RUN commands** (reduce layer count, clean up in same layer)
7. **Pin specific versions** (avoid pulling unexpected large updates)

---

**Q18: What is the difference between `EXPOSE` and `-p` (port publishing)?**

**A:**
- **`EXPOSE`**: A documentation directive in the Dockerfile. It tells others which port the app listens on but does NOT actually publish the port. It's metadata only.
- **`-p` (or `--publish`)**: Actually maps a host port to a container port, making the service accessible from outside the container. Example: `-p 3000:3000` maps host port 3000 to container port 3000.

You can run a container without `EXPOSE` and still publish ports with `-p`. And having `EXPOSE` without `-p` means the port is NOT accessible from the host.

---

**Q19: How would you debug a container that keeps crashing?**

**A:**
1. **Check logs**: `docker logs <container>` — see what error occurred
2. **Check events**: `docker events` — see container lifecycle events
3. **Inspect the container**: `docker inspect <container>` — check config, exit code
4. **Run interactively**: `docker run -it <image> sh` — get a shell to debug manually
5. **Check health**: `docker inspect --format='{{.State.Health}}' <container>`
6. **Override the entrypoint**: `docker run -it --entrypoint sh <image>` — skip the normal command and explore the filesystem

---

**Q20: Explain the difference between `docker compose up` and `docker compose run`.**

**A:**
- **`docker compose up`**: Starts all services defined in the compose file (or specific ones), creates networks and volumes, and maintains the lifecycle of all services together.
- **`docker compose run`**: Runs a one-off command against a specific service. It creates a new container for the command, uses the service's configuration (volumes, networks), but doesn't start dependent services by default (use `--service-ports` to expose ports).

```bash
# Start everything
docker compose up

# Run a one-off migration command
docker compose run app npm run migrate
```

---

**Q21: What are Docker image layers shared between containers?**

**A:** Since layers are read-only and content-addressed (identified by SHA256 hash), multiple containers can share the same image layers. If you have 5 containers running from the same image, the image layers exist only once on disk. Each container only adds its own thin writable layer on top. This is why Docker is so space-efficient compared to virtual machines. Even different images that share the same base (e.g., `node:22-alpine`) share those base layers.

---

**Q22: How do you handle secrets (passwords, API keys) in Docker?**

**A:** Never put secrets in:
- Dockerfiles (`ENV PASSWORD=secret` — visible in image history)
- Docker Compose files committed to Git

Instead:
1. **Environment variables** (passed at runtime): `docker run -e DB_PASSWORD=secret my-app`
2. **`.env` file** (not committed to Git): Referenced in docker-compose.yml
3. **Docker Secrets** (Docker Swarm): Encrypted at rest, mounted as files
4. **External secret managers**: HashiCorp Vault, AWS Secrets Manager, etc.

```yaml
# docker-compose.yml with .env file
services:
  app:
    environment:
      - DB_PASSWORD=${DB_PASSWORD}  # Read from .env file
```

### Scenario-Based Questions

---

**Q23: Your Docker build takes 5 minutes. How do you optimize it?**

**A:**
1. **Fix layer ordering** — Move `COPY package*.json` before `COPY . .` so `npm install` is cached
2. **Use `.dockerignore`** — Stop copying `node_modules`, `.git`
3. **Multi-stage build** — Reduce final image size
4. **Use `npm ci`** — Faster than `npm install`
5. **Pin base image** — Avoid re-downloading changed `latest` tags
6. **Use BuildKit** — `DOCKER_BUILDKIT=1 docker build .` (parallel layer builds)
7. **Cache mount** — `RUN --mount=type=cache,target=/root/.npm npm ci`

---

**Q24: Your MongoDB data disappears every time you restart the container. How do you fix it?**

**A:** Use a Docker volume to persist MongoDB's data directory:

```bash
docker run -d \
  --name mongo \
  -v mongo-data:/data/db \
  mongo:7
```

The `-v mongo-data:/data/db` mounts a named volume at MongoDB's data directory. Even if the container is removed and recreated, the data persists in the `mongo-data` volume.

---

**Q25: Your Express app can't connect to MongoDB running in another container. What's wrong?**

**A:** Most likely one of these issues:
1. **Not on the same network**: Both containers must be on the same custom Docker network
2. **Using `localhost`**: Inside a container, `localhost` refers to the container itself, not other containers. Use the MongoDB container's name as the hostname (e.g., `mongodb://mongo:27017`)
3. **Using default bridge network**: DNS resolution doesn't work on the default bridge. Create and use a custom network.
4. **MongoDB not ready yet**: The app might start before MongoDB is fully initialized. Use `depends_on` with health checks in Docker Compose.
